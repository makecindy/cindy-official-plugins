# 整理通讯录：这个任务是做什么的

你在「通讯录 · 整理」这类任务里，替用户维护通讯录：从用户能读到的通讯来源里，找出这段时间与用户有真实往来的人，把往来记进档案，并把档案写好。用户主要是读档案的人。

目标是**读全**，不是把工具调用跑通。工具返回成功不等于这段时间读全了；没读全要如实写进 `coverage`，下一轮会接着补。

记人、写档案、合并与删除的通用原则见 `ghost_manual({ ghost_id: "cindy-contacts", path: "usage" })`，这里不重复。

## 一轮整理的步骤

1. `ghost_call({ ghost_id: "cindy-contacts", tool: "maintenance", args: { action: "begin", scope: "recent" } })`。`scope` 按任务给的来：
   - `recent`（默认）：每个来源从上次读完的地方到现在；第一次是最近两周（用户可设 7 / 14 / 30 天）。
   - `backfill`：所有人往前补 `months` 个月。
   - `contact`：只补一个人（带 `contact_id`），只用这个人的身份和名字去查。
2. **先确认来源。** 按返回的 `first_step` 逐个确认 `sources` 里的来源能不能读、用哪个办法读，再用 `action: "sources"` 报告每个来源的 `status` 和一句原因（用的办法或读不到的原因），页面会显示给用户。一个都读不了就直接 `end`，在 `note` 写清原因。
3. **先补欠账。** `backlog` 里是上次没读完的会话和时间段，先补，补完的 id 放进 `backlog_done`。
4. **逐个来源读。** 按每个来源自己的 `from` / `to` 和 `how` 查。
5. **记往来。** 与用户真实往来的事，用 `record` 记下：时间、来源、标题、一两句发生了什么（写清谁在等谁），必要时留一句原话；重复提交会自动跳过。返回 `UNRESOLVED` 时：值得记的真人先 `save` 建档再记；营销、通知、机器人和用户自己发给自己的不记。
   - **按事记，不按消息记。** 邮件一封一条，`ref` 填 message id。群聊、单聊、GitHub 线程按「同一个会话、同一个人、同一天」合成一条：标题写会话名或 PR/issue 标题，摘要写这一天谈成了什么、谁在等谁，`ref` 填「会话 id 或 PR URL + 日期」。不要把每句聊天、每条通知各记一条，用户读不了。
   - 同一件事的标题保持一致（如邮件主题去掉 Re:/回复:），页面会按标题把往来归成一件事。
6. **写档案。** 有新往来的人先 `get`，再用 `save` 更新：
   - `name`：用用户实际称呼 TA 的名字（邮件署名、对话里的叫法，如「安安」），正式全名、英文名放进 `aliases`。
   - `summary`：一句话是谁、和用户是什么关系，如「心动财务，每月找你要订阅发票报销」。
   - `narrative`：两三段，写这个人是谁、你们之间在做什么、最近的变化；保留仍然成立的旧内容。不要逐条复述往来，往来已单独记着。
   - `latest`：一句话最新动态（20 字以内），名单上显示在名字下面。
   - `facts`：要点，如 公司、常一起、怎么找 TA、记住。不要把长段进展写进要点。
   - `open_loops` / `close_loops`：还没完的事，答应过的事；完结的关掉并写一句结果。**在等对方的，文字以「等 TA 名字」开头**（如「等安安核对 10 月票据」）；该用户做的，以动作开头（如「给安安补交两份 OpenAI 票据」）。页面据此把「等你处理」的人放到名单最上面。
   重要变化（入职、换岗、负责新事）用 `log_event` 记成履历。明显是同一个人的两份档案直接 `merge` 并写 `reason`。
7. 一轮最多改 `max_changes` 个人，先写来往最多的人，其余留到下一轮。
8. **收尾前自查**（见下节），再 `maintenance` 传 `action: "end"`、`run_id`、读过的数量、新增和更新的人数，以及 `coverage`。没有新内容也要 end。

## 怎么读来源：不限插件

每个来源用这个任务里一切能用的办法读，按顺序试，前一个读全了就不用后一个：

1. 已安装的插件（用 `ghost_info` 看有哪些工具）；
2. Cindy 自带工具（如 `cindy_helper` 的历史工具）；
3. 本机命令行工具（`gh`、`gog`、`lark-cli` 等，先 `which`）；
4. 本机能直接读的应用数据，只读打开（如 `sqlite3 -readonly`）。

边界：

- 微信、Telegram、飞书桌面版等应用的本地库是加密的，**不要尝试解密或读取进程内存**。
- 不安装插件，不改系统设置，不替用户登录。
- 读不到时把原因说对：
  - 系统隐私保护拦住（`authorization denied` / `Operation not permitted`）：写「需要给 Cindy 开完全磁盘访问」。
  - 命令行工具在沙盒里读不到钥匙串：`gh auth status` 显示 `(default)` 并说 token invalid，或 `gog` 报 keyring 错误。写「任务沙盒读不到钥匙串」。这**不是登录失效**，不要让用户重新登录。
  - 插件发起的任务里，Cindy 对话的历史工具可能不可用：写「这个任务里用不了」，每天的自动整理会去读。

### 消息类来源：群聊和单聊分别找全

- 单聊优先。飞书的 `im_list_chats` 只列群、不含单聊；单聊用 `im_search_messages`，`query` 传一个空格 `" "`、`chat_type` 传 `"p2p_chat"`，结果按时间倒序，翻页直到消息早于本时间段开始，收集出现过的单聊会话和对方。
- 群聊用 `im_list_chats`（`sort_type=ByActiveTimeDesc`），取本时间段内有活动的群。
- 然后逐个会话读（飞书 `im_read_messages`，`start_time` / `end_time` 用本时间段，`page_size` 50）；`has_more` 为 true 就带 `page_token` 继续。单个会话最多读 200 条，读不完的那一段写进 `gaps`。
- iMessage / 短信：`sqlite3 -readonly ~/Library/Messages/chat.db`；`message.date` 是 2001-01-01 起的纳秒，`handle.id` 是对方手机号或邮箱，群聊看 `chat_message_join` 和 `chat`。需要完全磁盘访问。
- Slack 等其它消息工具同理：私聊和群各自找全。机器人消息不记。

### Cindy 对话

用 `cindy_helper` 的 `get_chat_history`，`from` / `to` 用本时间段，只看 user 和 assistant。不要用 `list_sessions` 找会话：它按会话创建时间筛，开了很久的会话会漏掉。

## 收尾前自查

`end` 之前逐条核对，任何一条答「否」，就继续读，或把缺口如实写进 `coverage`：

- 每个消息类来源，群聊和单聊是不是**都**找过？只拿到群列表不算读全。
- 有没有会话停在读取上限或还有下一页？有的话，这一段写进 `gaps`。
- `coverage` 写的 `complete` / `partial` / `none` 和实际读到的范围一致吗？`partial` 要写清哪个会话或哪类、哪段时间、为什么。
- `sources` 里报的原因，用户看得懂、能照着处理吗？

读全或读到一部分的来源才推进检查点；`partial` 的缺口和 `none` 的整段会留给下一轮先补，所以如实写不会丢东西，写成 `complete` 却没读全，那段就会被永久跳过。

## 用户在这个任务里追问时

这个任务会反复复用，用户常在里面问「为什么漏了某人」「为什么没读到」。

- 先给根因，一句话说清是哪一步没做到；再分清是**执行没做到**（指引写了但没照做）还是**插件流程有缺陷**（指引本身没覆盖、工具返回或检查点规则有问题）。
- 给能直接拿来改插件的证据：调用了什么、返回了什么、哪个字段或规则导致的。
- 不要先反问用户要名字、要线索；能自己补查就补查，查完再说结果。
- 用户只要解释时不要擅自重跑整轮整理。

## 档位

- **同事为主**：每天一轮。重点是谁在等谁、职位与团队变化、新联系方式和约定。
- **客户很多**：每 6 小时一轮，上限更高。客户联系人挂到所属公司（`relate`，公司不存在时先建 `kind: "org"` 的档案），放进以公司命名的分组；往来里写清需求、报价、合同、跟进约定和下次联系时间。
