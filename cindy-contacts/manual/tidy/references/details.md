# 整理通讯录：按需查阅的详细规则

你在「通讯录 · 整理」这类任务里，替用户维护通讯录：从用户能读到的通讯来源里，找出这段时间与用户有真实往来的人，把往来记进档案，并把档案写好。用户主要是读档案的人。

目标是**持续补全，同时让每轮成本有界**。新内容优先；工具返回成功不等于读全，没读完的精确位置持久保存，下一轮续接。不要为清空历史欠账每天从头重扫，也不能为省 token 把未处理内容标为完成。

记人、写档案、合并与删除的通用原则见 `ghost_manual({ ghost_id: "cindy-contacts", path: "usage" })`，这里不重复。

## 完整流程与档案写法

1. `ghost_call({ ghost_id: "cindy-contacts", tool: "maintenance", args: { action: "begin", scope: "recent" } })`。`scope` 按任务给的来：
   - `recent`（默认）：每个来源从上次读完的地方到现在；第一次是最近两周（用户可设 7 / 14 / 30 天）。
   - `backfill`：所有人往前补 `months` 个月。
   - `contact`：只补一个人（带 `contact_id`），只用这个人的身份和名字去查。
2. **复用可用来源。** `previous_sources` 提供上轮路径。一次实际增量查询成功即确认可读，不再另外遍历同源插件、CLI 和本地库。路径失败才查替代；无权限/环境变化时不每天重复探测全部入口。用 `action: "sources"` 报告本轮实际状态；一个都读不了就直接 `end`。
3. **先新后旧，遵守预算。** 先处理 `sources` 各自的新窗口。只有剩余预算才补本轮返回的 `backlog`；其余由插件保留，不自行遍历全部欠账。`budget` 限制本轮索引条数、正文读取、来源查询次数、补读项和补读索引条数，补读计入总预算；任一达到就保存精确缺口并收尾。预算是 Agent 执行上限，插件无法强制截断外部工具调用。任务明确每周补读时遵守任务频率。
4. **索引先行。** 按每个来源自己的 `from` / `to` 和 `how` 查，只返回 id、时间、参与人、主题、短摘要和分页信息；先批量 `filter`，再为未处理的真人往来读取必要正文。未知真人仍需判定，不限于已有联系人。批量执行来源查询时只把精简结果交回模型，不输出整封 MIME、无关工具 JSON 或完整历史线程。
5. **记往来。** 与用户真实往来的事，用 `record` 记下：时间、来源、标题、一两句发生了什么（写清谁在等谁），必要时留一句原话；重复提交会自动跳过。返回 `UNRESOLVED` 时：值得记的真人先 `save` 建档再记；营销、通知、机器人和用户自己发给自己的不记。
   - **按事记，不按消息记。** 邮件一封一条，`ref` 填 message id。群聊、单聊按「同一个会话、同一个人、同一天」合成一条：标题写会话名，摘要写这一天谈成了什么、谁在等谁，`ref` 填「会话 id + 日期」。不要把每句聊天、每条通知各记一条，用户读不了。
   - **GitHub 不记往来、不开待办。** 它只用来补全资料：给已有的人补上 GitHub 账号，在 `facts` 写「常在仓库」「常做」（负责哪一块）。PR、review、评论都不用 `record`（会被拒收）。
   - 同一件事的标题保持一致（如邮件主题去掉 Re:/回复:），页面会按标题把往来归成一件事。
6. **有变化才写档案。** 按人聚合本轮新往来，每人先 `get({ id, compact:true })` 一次（最近 5 条往来/事件，人物资料与待办保留）；不足以判断才完整 get。只用 `save` 更新有实质变化的字段，不因 record 返回重复就重写。补读旧消息时保留较新的 latest 与已解决结果：
   - 联系方式：邮件签名、名片、对话里出现的手机号、微信、LinkedIn 主页等，用 `identities` 补上（LinkedIn 用 `linkedin` 平台，填主页链接）。
   - `name`：用用户实际称呼 TA 的名字（邮件署名、对话里的叫法，如「阿明」），正式全名、英文名放进 `aliases`。
   - `summary`：一句话是谁、和用户是什么关系，如「心动财务，每月找你要订阅发票报销」。
   - `narrative`：两三句人话，像向朋友介绍这个人：是谁、在哪里做什么、和用户是什么关系、最近在一起做什么。不写邮箱、账号、PR / issue 编号、日期流水，也不写「已核实、对应」这类整理过程；联系方式放 identities，核实依据不用写进介绍。原文里已有的流水账在改写时压成一两句结论，不要接着往后追加。
   - `latest`：一句话最新动态（20 字以内），名单上显示在名字下面。
   - `facts`：只写短而稳定的要点（每条 20 字内），如 公司、职位、怎么找 TA、称呼偏好。进展、结果、日期流水不写进要点。
   - `open_loops` / `close_loops`：**只记两种事**——有人明确请用户做的（要文件、要回复、要审批）、用户明确答应别人的；以及用户明确在等对方交付的。**在等对方的，文字以「等 TA 名字」开头**（如「等阿明核对 10 月票据」）；该用户做的，以动作开头（如「给阿明补交两份 OpenAI 票据」），一句话写完，`detail` 不超过 30 字。
     - 不记你自己的跟踪备注：「跟进 X」「确认 X」「核对 X」「补核 X 的验收」这类不是待办，PR、工单的进展写进往来即可。页面会把这类文字和 14 天前发起的事收起来，不算「等你处理」。
     - 每人同时开着的不超过 3 件。整理时先看已开着的：已办成、对方已回复、或 14 天没有新进展的，用 `close_loops` 关掉并写一句结果，不要只改写措辞让它继续开着。
   重要变化（入职、换岗、负责新事）用 `log_event` 记成履历。明显是同一个人的两份档案直接 `merge` 并写 `reason`。
7. 一轮最多改 `max_changes` 个人，先写来往最多的人，其余留到下一轮。
8. **收尾前自查**（见下节），再 `maintenance` 传 `action: "end"`、`run_id`、读过的数量、新增和更新的人数，以及 `coverage`。没有新内容也要 end。

## 扫描回执与断点

- `maintenance({ action:"filter", source:"mail", account:"gmail:work@example.test", refs:["message-id-1","message-id-2"] })` 返回 `unseen` 和 `skipped`。每批最多 100 个 ID，**读正文前**使用；filter 不会写已处理标记。
- `account` 用稳定的服务商+账号/工作区标识，两个邮箱不能共用。邮件 ref 用不可变 message id，不能用 thread id 或发件人；可变日程用 `event id + updated/revision`。聊天扫描回执用消息 ID（已保存的按日合并往来仍沿用 usage 规则），不要用当天 chat id 跳过当天后续新消息。
- 完成该条内容涉及的**全部人物**的 `record` 和必要的 `save`，或根据索引确认是纯营销/机器人/无关通知后，批量 `ack`（参数同 filter）。失败、未读、没有处理完、达到人数上限的不能 ack。先 record 后崩溃但未 save 的内容下次仍会返回；重复 record 后补齐尚未保存的档案，再 ack。
- `scope:contact` 只处理目标人物时，不写全局 ack，除非已确认该条内容涉及的全部人物都已处理；不能让局部回补阻止日后全量整理发现其他参与人。
- `ack` 是本机整理回执，不存正文或凭证，不同步到另一台电脑；自动化只保留一台主执行电脑。换电脑可能重新扫描索引，不表示联系人往来会重复写入。
- 新窗口读取中达到预算，用 `coverage.partial.gaps` 保存**精确账号/会话与剩余范围**，不要把已读完整的来源整段再登记。分页的 gap 带 `resume:{ account, query, cursor }`，分别是稳定账号、原始查询（包含固定起止时间等筛选条件）和下一页 token；不要放访问令牌或可执行命令。缺口必须覆盖尚未处理的其余账号/会话；扫描完成但档案尚未保存也属于缺口。
- 历史补读每处理完一页，立即 `maintenance({ action:"progress", run_id, backlog_id, status:"partial", remaining:{ where, from, to, reason, resume:{account,query,cursor} } })`，只保留未读部分。分页时保留原 account/query；供应商 token 失效则清空 cursor，用同一查询重新列索引并 filter，不能声称完成。
- 没有前进（权限、限流、附件确实必须但仍读不到）用 `progress` 的 `status:"blocked", note`；原断点保留，重试间隔按连续失败次数为 1、2、4、7 天。未尝试的欠账不用报 blocked，不改变它的失败次数。补完用 `status:"complete"`，或 end 的 `backlog_done`。不得把只补完第一页当整个欠账完成。
- 如果 `progress` 返回 `STALE_BACKLOG`，说明另一轮已更新这个断点。结束本轮的补读，不要重试旧页或把该缺口加到 `backlog_done`；下次以 `begin` 返回的位置为准。
- 旧版本没有 budget/filter/ack/progress 时不要调用不存在的 action；仍按任务预算、轻量索引与精确 coverage 收尾，原欠账保留，不伪造分页完成。

## 邮件与附件

邮件先按时间窗口取轻量索引，过滤已处理 ID，再判断是否需要正文。已有联系人没有新往来就不 get/save；同一批新往来只读一次人物档案。默认不展开历史整串、不下载每个附件；只有正文不足以确定具体人物信息或真实约定时，按需读取相关附件。不相关附件不是欠账，不能因为一封旧邮件带附件就让整个邮箱永久 partial。

## 怎么读来源：不限插件

每个来源复用一条已成功的读取路径，失败才按顺序寻找替代；不要每天遍历所有入口：

1. 已安装的插件（用 `ghost_info` 看有哪些工具）；
2. Cindy 自带工具（如 `cindy_helper` 的历史工具）；
3. 本机命令行工具（`gh`、`gog`、`lark-cli` 等，先 `which`）；
4. 本机能直接读的应用数据，只读打开（如 `sqlite3 -readonly`）。

边界：

- 微信、Telegram、飞书桌面版等应用的本地库是加密的，**不要尝试解密或读取进程内存**。
- 不安装插件，不改系统设置，不替用户登录。
- 读不到时把原因说对：
  - 系统隐私保护拦住（`authorization denied` / `Operation not permitted`）：写「需要给 Cindy 开完全磁盘访问」。
  - 命令行工具在沙盒里读不到钥匙串：`gh auth status` 显示 `(default)` 并说 token invalid，或 `gog` 报 keyring 错误。写「任务沙盒读不到钥匙串」。这**不是登录失效**，不要让用户重新登录。
  - 插件发起的任务里，Cindy 对话的历史工具可能不可用：写「这个任务里用不了」，每天的自动整理会去读。

### 消息类来源：群聊和单聊分别找全

- 单聊优先。飞书的 `im_list_chats` 只列群、不含单聊；单聊用 `im_search_messages`，`query` 传一个空格 `" "`、`chat_type` 传 `"p2p_chat"`，结果按时间倒序，翻页直到消息早于本时间段开始，收集出现过的单聊会话和对方。
- 群聊用 `im_list_chats`（`sort_type=ByActiveTimeDesc`），取本时间段内有活动的群。
- 然后逐个会话读（飞书 `im_read_messages`，`start_time` / `end_time` 用本时间段，`page_size` 50）；`has_more` 为 true 就带 `page_token` 继续。单个会话最多读 200 条，读不完的那一段写进 `gaps`。
- iMessage / 短信：`sqlite3 -readonly ~/Library/Messages/chat.db`；`message.date` 是 2001-01-01 起的纳秒，`handle.id` 是对方手机号或邮箱，群聊看 `chat_message_join` 和 `chat`。需要完全磁盘访问。
- Slack 等其它消息工具同理：私聊和群各自找全。机器人消息不记。

### Cindy 对话

用 `cindy_helper` 的 `get_chat_history`，`from` / `to` 用本时间段，只看 user 和 assistant。不要用 `list_sessions` 找会话：它按会话创建时间筛，开了很久的会话会漏掉。

## 收尾前自查

`end` 之前逐条核对，任何一条答「否」，就继续读，或把缺口如实写进 `coverage`：

- 每个消息类来源，群聊和单聊是不是**都**找过？只拿到群列表不算读全。
- 有没有会话停在读取上限或还有下一页？有的话，这一段写进 `gaps`。
- `coverage` 写的 `complete` / `partial` / `none` 和实际读到的范围一致吗？`partial` 要写清哪个会话或哪类、哪段时间、为什么。
- `sources` 里报的原因，用户看得懂、能照着处理吗？

读全或读到一部分且保存了精确缺口的来源才推进检查点；未处理内容继续保留。`complete` 只描述本轮来源窗口，不包含另行返回的历史 backlog。预算耗尽写 partial/none 后结束，不为追求 complete 继续翻页；把没处理的写成 complete 会导致遗漏。

## 用户在这个任务里追问时

这个任务会反复复用，用户常在里面问「为什么漏了某人」「为什么没读到」。

- 先给根因，一句话说清是哪一步没做到；再分清是**执行没做到**（指引写了但没照做）还是**插件流程有缺陷**（指引本身没覆盖、工具返回或检查点规则有问题）。
- 给能直接拿来改插件的证据：调用了什么、返回了什么、哪个字段或规则导致的。
- 不要先反问用户要名字、要线索；能自己补查就补查，查完再说结果。
- 用户只要解释时不要擅自重跑整轮整理。

## 档位

- **同事为主**：每天一轮。重点是谁在等谁、职位与团队变化、新联系方式和约定。
- **客户很多**：每 6 小时一轮，上限更高。客户联系人挂到所属公司（`relate`，公司不存在时先建 `kind: "org"` 的档案），放进以公司命名的分组；往来里写清需求、报价、合同、跟进约定和下次联系时间。
