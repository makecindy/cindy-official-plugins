# Background Follow-Up Round

Read this when woken up by a scheduled PR follow-up round (`SKILL.md` section 5), or when ending follow-up / toggling draft state.

Read the gate's event report; `--last-result --json` also provides `waitContext`. Follow any convergence instructions in `detail`. Refresh the named PR card first to verify ownership: on `existing_task`, do no work or gate acknowledgement; delete only this task's duplicate schedule after checking its target. If ownership is unknown, stop the round.

1. **Handle new work** as in `references/fix-round.md`: failed checks, feedback, conflicts and queue problems. On `base-moved` or a baseline wait's expiry, look for the fix on the base; when present, merge, verify and push it, then confirm CI started on the new head. If still blocked, record a wait; rerun only a confirmed flake, once. Reassess changed/expired waits and investigate unavailable data. A `silence-guard` is a chance to inspect what the gate cannot see. A `defer-expired` means continue with the results available.
2. **Refresh the card** before finishing, using `card_id`, `repo` and `pr`; add `to_latest: true` only when notifying below. If an older schedule has no card, create one with `following: true` and add its ID to the schedule prompt, preserving its timing and hook.
3. **Finish once**, using `node "<skill-dir>/scripts/pr-node.cjs" pr-heartbeat-gate.mjs <PR_URL>` with one of:
   - `--wait <plan.json>` when blocked: choose concrete targets and a useful review time from `waitContext`; see [Model-directed waits](follow-up.md#model-directed-waits). A CI failure this PR did not cause (it fails on the base, or shared tooling, dependency install or infrastructure broke) is a `baseline` wait even if base CI passes intermittently; pass `afterMinutes: null` and the program backs off from 15 minutes to 12 hours, looking within an hour after the base moves. Use `human` only when a person must act on this PR itself. A human wait that only awaits approval or the merge may use `afterMinutes: null`. One that sets a failing check or an open thread aside for a human comes back within a day: confirm the reason still holds (the base may have fixed or dismissed it) before waiting again.
   - `--resume "<what was handled or pushed>"` after resolving work or pushing. This clears the wait; the existing bot-review window handles the new commit.
   - `--ack` when no blockers or wait remain.
   Read the receipt; correct a rejected decision in this round. Reporting “waiting” in chat does not record a wait.

**Stop conditions.** Merged/closed → report once (including when the pre-run gate's explicit user-authorized auto-merge merged the PR directly), end following, then `references/cleanup.md`. `auto-merge-unknown` / `auto-merge-rejected` → notify the user with the exact detail, check the PR state manually, and never retry an unknown merge automatically. `comment-limit` → end following and explain. `draft-entered` → end following unless the user requested draft following or their saved preference allows it. While following a draft, fix normally but do not mark it ready without authorization.

**Continuing-follow decision rule (first handoff, background rounds and Worker handoffs).** When continuing observation is authorized, establish or retain the verified follow-up schedule first. If a particular change needs authorization, do the authorized read-only investigation or preview first; do not execute the change. Keep observing independently of the decision. In the conversation where the user requested the work, send an ordinary message stating what you did, the proposed action and its impact, your recommendation, and one concrete question the user can answer in text. Do not use a blocking question tool or decision card for this decision. If an existing Worker or dedicated task owns the schedule, relay that message to the originating conversation using the existing handoff, with enough context for the user to answer; do not ask only in the Worker task or create another schedule. Preserve that ownership. Do not treat silence as authorization, require approval of a change to keep observing, or ask again for already authorized work. If the user explicitly requested observation only or said not to ask for execution, respect that limit and report the facts without soliciting permission. This does not change the PR publishing and start-following card offers.

**Notifications.** Every actual follow-up round ending with a still-relevant user decision must apply the continuing-follow decision rule above again, even if asked earlier or this round found no GitHub changes. Call `schedule_notify_current_run` for background reports and bring the PR card to the latest reply. A passive “waiting for confirmation” status is not enough. Record the applicable wait as in step 3 and end the round without awaiting a reply; the existing schedule continues.

Stay silent for observation-only polls and rounds with no user decision or reportable event — including waiting for another reviewer's approval or an already-authorized merge, autonomously fixing failures and pushing to rerun CI, or recording a timed CI/baseline wait (without a `notice`) while waiting for an external fix. If merging actually needs this user's authorization, it is a user decision and follows the rule above. On `checks-failed` or `checks-finished`, inspect the current snapshot and handle the failures (fix and push, or record the applicable wait); stay silent unless a user decision is required, the `--wait` receipt carries a `notice`, or the same problem stays stuck through several backoff cycles. Also notify (calling `schedule_notify_current_run` and bringing the PR card to the latest reply) for merged/closed, following stopping itself, a problem stuck through several backoff cycles, or a `notice` in the `--wait` receipt. Both `notice: entered` and `notice: reminder` require a message in this round: say who must act and what is needed. When the user can decide (merge with an optional check failing, dismiss an alert, approve a workflow run), ask that specific question with a recommendation instead of merely saying “waiting for a maintainer” or asking only whether to keep following. When only somebody else can act, report that accurately without inventing a decision for the user. A missing `notice` never suppresses a known pending user decision.

## Ending following

Before deleting a schedule, confirm its ID, PR, task and exact plugin-generated hook in a fresh read. For a reused or discovered existing schedule, the host lacks conditional deletion: leave it intact and guide the user to stop it in Automation settings using the verified ID. The same applies when the hook has been replaced with a custom command. Do not report stopped until the scheduler confirms absence. Otherwise delete the schedule and verify deletion first; then set `following: false` on its card (add `to_latest: true` when notifying). If deletion is uncertain, keep the reservation and resolve it. This order also applies to foreground cleanup and a user stop request (do not run the full background-round steps above for a foreground stop).

## Older schedules

The plugin can identify the exact old generated `node "<skill-dir>/scripts/pr-heartbeat-gate.mjs" <PR_URL>` hook in the owning task, including a legacy following card whose ID was not saved, when a unique matching schedule and its exact plugin-generated hook are verified by the final read, whether active or paused. A paused schedule stays paused; a missing schedule is stopped, and an ambiguous, foreign or custom hook is not adopted. If verification is temporarily unavailable, keep the old claim unverified and retry on an ordinary card refresh; do not start or stop another schedule before verification. This read-only check also applies to already-authorized draft followers, but merely displaying a draft does not start one. The public scheduler tool cannot make a conditional update against the configuration just read, so leave the saved hook and timeout unchanged. If the card returns `legacy_hook_repair`, report the schedule and replacement command to the user; ask them to change only the command in Automation settings. After the user saves it, verify the same schedule ID and the hook, then let the existing schedule run. Do not replace or delete a custom same-name script, change other settings, or create another schedule. The launcher filters idle firings; five-minute checks do not imply five-minute model calls.

## Draft and ready

When the user asks in text to mark a draft ready, run `gh pr ready <PR_URL>`, refresh the card (`pr_card` with `card_id`, `repo`, `pr`) and apply its follow setting as after opening. When they ask to turn a PR back into a draft, run `gh pr ready --undo <PR_URL>`; if it was being followed, stop following as in `## Ending following` above, then refresh the card. (Foreground draft/ready requests do not run the full background-round steps above.)
