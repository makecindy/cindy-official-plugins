# Setting Up Background Follow-Up

Read this when setting up, handing off, or deduplicating a background PR follow-up schedule (`SKILL.md` section 4) — for example on an older host where `pr_card` does not return `follow_state`, in IM channels, in group chats / unrelated source tasks, or when taking over an existing PR.

**Local checks are required; remote discovery is optional.** Deduplicate on the computer hosting the PR task with `schedule_list`, `device: "local"`, and no status filter. If other computers are already known to be online and a bounded lookup is available without noticeably delaying startup, you may make one best-effort remote lookup for the exact PR URL. Allow at most five seconds of additional waiting across all online computers, not five seconds per computer; if the available tool cannot bound that wait, skip the remote lookup. Exclude computers already reported offline before dispatch: do not query them, probe them, reconnect to them or wait for them to come online. If a computer goes offline during the lookup, skip it immediately. Offline computers are outside the lookup scope, not unresolved dependencies or reasons to ask the user to bring them online. Never retry remote discovery or require complete cross-device coverage. A remote timeout, error or `partial: true` does not block local startup; successful device results in a partial response are still usable. If the lookup promptly confirms an active schedule for this exact PR in a dedicated PR task, reuse it without creating a local duplicate or claiming the current task is following. A paused, expired or unverified remote schedule is not an active follower and does not block local startup; do not change it. Otherwise proceed using the local result. Apply this policy to direct starts, group-chat handoffs and restarts, sharing the single remote lookup result across the handoff rather than repeating it in the destination task. Verify a created schedule on its actual device; verification of a reused remote follower must also fit the same waiting budget, otherwise fall back to local startup. Keep duplicate protection between tasks on this computer.

**When to follow:** when the user asked you to (including `/pr <link>` and the PR card's "Auto-follow until merged" button), or when the card's "Follow after opening" setting or their saved preference says so. With a PR card, its button and setting are the offer: do not also ask in text. Without a card, first read `pr_follow_settings`; apply an enabled preference without asking again. Only when no instruction or preference enables following, offer it once in one short sentence: you can keep following it in the background, fixing CI and review feedback and telling them when it is ready or needs them. If the user answers "always" or "never", save that preference where your memory tools allow and do not ask again. Do not follow draft PRs unless asked, or unless the user's saved preference says to follow drafts too: a draft is still being worked on. A draft's card offers "Mark ready for review" instead; the plugin converts it itself and, when the card's setting says so, then asks you to start following.

**Group chats and unrelated source tasks:** first confirm the PR is still open; if merged/closed, report that terminal state without creating a new follow-up. Otherwise keep this PR's background work in its own Cindy task. First find an existing schedule for the exact PR URL on the current device (`schedule_list` with `device: "local"`, no status filter); inspect its target before reusing it. Apply the optional, bounded remote discovery above; an unavailable or slow computer must not block this handoff. Reuse an existing dedicated PR task when known. Otherwise discover `cindy_helper` `send_to_session` and create one with the `#<number> <short topic>` task title from `references/publish.md` §2, the existing repository as `working_dir`, and `use_worktree: true`. Pass the exact PR URL, known follow preferences/model, original task context, authorization limits and a request to establish and read back the schedule. Keep the source group name and conversation intact. The dedicated task owns its card and schedule; bind there, never to the group or an unrelated dispatcher. The source task's card may already hold a start reservation (clicking the button saves `pending: 'follow'` there before the click reaches you). Before the handoff, verify no schedule targets the source task, then release that reservation with `pr_card` using the source `card_id` and `following: false`; otherwise the dedicated task's `claim_follow` returns `existing_task` pointing back at the source and cannot start. The dedicated task then claims with its own card. Creation/delivery is only a handoff: query `schedule_list` / `schedule_get` for that target (or read its verified receipt) before reporting success. If still pending, say setup is pending. If handoff fails, report that following has not started; do not silently bind to the group. Do not create another independent task inside an already dedicated PR task.

Before creating or restarting a follow-up, call `pr_card` with `repo`, `pr`, `claim_follow: true` and the existing `card_id` if known, even if the task already has a card. This atomically reserves following for this task. Continue only after success with `follow_claimed: true`. `existing_task` means another task is following: keep the in-card link and stop here. `card_shown: false` (an IM channel, or the card could not be delivered) does not change the claim: `follow_claimed: true` still permits creating the schedule, and `existing_task` still means stop; report the follow-up state in text instead. A false or missing `follow_claimed` is not permission to create a schedule. Keep the returned `card_id` for the schedule prompt. The reservation only lasts until a schedule for this task exists: on every path that ends without creating one here (another task's schedule, a reused remote follower, a failed creation), verify no schedule targets this task and release it with `following: false`. Do not bypass this check when the state cannot be verified.

Use `cindy_scheduler` (`list_tools` with category `scheduler`, then `call_tool`). First `schedule_list` with `device: "local"` and without a status filter and look for a schedule whose prompt or `preRunHook.command` contains this exact PR URL (host, owner/repo and number). If one exists, check its target and status: an active schedule bound to the dedicated PR task can be reused; paused or expired is not running and still must not be duplicated. Resume or repair only within the current authorization, and never create a second schedule to hide a binding or status problem. A failed local query must be resolved before creating a schedule. Reuse a promptly verified remote follower when available under the optional discovery policy above. If a local schedule belongs to another task, or you reuse a verified remote follower, stop without claiming this task is following; release only this task's unused reservation with `following: false` after verifying no schedule targets this task. Keep that schedule intact. Otherwise inspect the local scheduler’s advertised `schedule_create` parameters. When it supports `prTrigger`, include the ordinary PR trigger shown below. On older hosts omit that field and keep the same pre-run check and timer. Call `schedule_create` once:

```json
{
  "name": "PR #<number>",
  "prompt": "Follow <PR_URL> with the pr Skill of Cindy's GitHub plugin (background round): load it first (in Claude Code it sits under the plugin `cindy-plugin-cindy-github`; if this session does not offer it, read <skill-dir>/SKILL.md) and follow its section 5. Checkout: <worktree path> (branch <branch>).",
  "cronExpr": "*/5 * * * *",
  "intervalMs": 300000,
  "prTrigger": { "url": "<PR_URL>", "change": "any" },
  "timezone": "<the user's IANA time zone>",
  "recurring": true,
  "bindToCurrentSession": true,
  "silentWhenIdle": true,
  "agentKind": "<claude-code, codex or pi: the agent running this task>",
  "notify": { "desktop": true, "feishu": false },
  "preRunHook": {
    "command": "node \"<skill-dir>/scripts/pr-heartbeat-gate.mjs\" <PR_URL>",
    "timeoutMs": 180000
  }
}
```

- Add a line to the prompt only for facts specific to this PR that cannot be derived (for example a reviewer the user named), and `PR card: <card_id>.` when there is one. General procedure lives in this Skill, not in the prompt.
- The prompt names `<skill-dir>/SKILL.md` because a task whose agent runs on another computer (a remote or shared provider) may not offer this Skill there, while its shell still runs on this computer.
- The hook is a check that ships with this Skill: mount it directly, never generate one with `schedule_set_pre_run_hook` or copy the script. Do not pass `workingDir`.
- **Model.** When `pr_follow_settings`, the card's settings or the click event carry `follow_model`, the user chose the model for following: pass its `model_agent_kind` as `modelAgentKind`, plus `providerId`, `model`, `effort` (omit when empty) and `fastMode` from it, and its `agent_device_id` as `modelAgentDeviceId` when present (a model on another computer or a shared provider), then confirm them in the `schedule_get` read-back. Without `follow_model`, pass none of these so each round uses this task's model. If the scheduler rejects the chosen model, say so in one line and create the schedule without it rather than guessing another.
- The hook path must be the resolved `<skill-dir>`. Never put a path under the system temp directory (for example one containing `cindy-claude-skills-`) in the hook: it disappears when Cindy restarts. Resolve it right before creating the schedule: run `realpath` on the base directory Cindy gave when this Skill was loaded. If that directory no longer exists, load this Skill again for a fresh one. Never search the disk for it.
- `notify` values are JSON booleans. On `INVALID_ARGS`, fix the arguments once from the returned schema; if it fails again, report it.
- A returned id is not proof. On hosts that accepted an explicit PR trigger, verify the saved trigger names this PR and change `any`. Read it back with `schedule_get`, confirm `status: active`, the exact PR URL and intended target session, confirm its `preRunHook.command` points at this Skill's update-stable entry (the path contains `/agent-skills/skills/`), and confirm it appears in `schedule_list`. The prompt's fallback must name the `SKILL.md` in that same update-stable directory: the directory you resolved is a per-version copy that is removed after later plugin updates, so when the saved prompt names it, replace only that path with one `schedule_update` of the prompt. Tell the user in one line that following started and how to stop it ("say stop following", or the card's Stop button), and update the card with `following: true`.
- If creation clearly fails, first confirm no schedule for this PR was created in this task, then release the reservation with `pr_card` and `following: false`. An unknown result requires a read-back; do not release and retry blindly.
- Leave `cronExpr` and `intervalMs` alone afterwards. The check paces itself from what it last saw: most firings end at once without calling GitHub, an inferred approval-only state is looked at every 30 minutes, an explicit wait still checks for new work every 5 minutes without calling the model, and Cindy fires the schedule at once when its title-bar PR status shows a change. How the check decides is described in `references/follow-up.md`.
