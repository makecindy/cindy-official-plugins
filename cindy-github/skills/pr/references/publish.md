# Starting Work and Opening a Pull Request

Read this when starting a change that will become a pull request or opening a PR (`SKILL.md` sections 1 and 2).

## 1. Start the work

For a change that will become a pull request (not for a question or a read-only investigation):

- **Already isolated:** if the task already works in a worktree or feature branch made for this same change, keep using it. A branch left over from another change does not count: create a task worktree instead of stacking unrelated commits on it. Fetch the target repository’s default branch and merge the fetched tip if the work branch is behind.
- **Otherwise create a task worktree:** call `cindy_helper` → `create_task_worktree` (category `control`; pass `repo_dir` when the task directory is not the repository itself). Cindy creates a branch from the freshly fetched remote default branch, binds the worktree to this task and removes it when the task is archived. The task itself does not move: run every shell command from the returned `worktree_path`, use absolute paths inside it for edits, and re-read the repository's rules there (the main checkout may be older). Keep using that path after restarts and context compaction. If the tool returns `base_fetched: false`, tell the user the base may be stale. Before opening the PR, successfully fetch its target branch from the target repository and merge the fetched tip. If fetching still fails, report that the base is still unverified.
- **Fallback** when the tool is unavailable or fails: fetch the default branch from the PR target repository (usually `upstream` in a fork checkout or `origin` otherwise). On success, run `git worktree add --no-track -b <branch> ../<repo-folder>-<slug> FETCH_HEAD` and work there. If fetching fails, report that the base is still unverified.

## 2. Open the pull request

**Task title:** whenever this workflow renames the PR’s own task or creates a dedicated follow-up task, use `#<number> <short topic>` (for example, `#1234 修复登录状态`). Summarize the core change in the user's language as a short phrase; preserve distinguishing technical names, but omit `PR`, workflow prefixes such as “Follow” / “跟进”, conventional-commit prefixes such as `fix:`, and redundant detail. Do not copy the full PR title or change the title on GitHub. Use `cindy_helper` `set_current_session_title` for an existing task only when automatic renaming is enabled or the user requests it.

**Explain the change before offering to publish.** Once the work is verified, give a concise, self-contained summary in the conversation before showing the PR card or asking in text. Lead with the problem and resulting behavior, then the main changes and verification results; mention material limitations when present. Use plain language and scale the detail to the change: a small fix may need only a few sentences. File names, diff statistics and a card alone do not explain what the PR does. Base the summary on the final diff, including related uncommitted work. If the user already asked to publish, give the same brief explanation and proceed without another approval round.

**Use visuals when they clarify the change.** A before/after screenshot can explain a UI change; a small diagram can explain a flow or interaction. Keep simple changes textual. Show any proposed screenshots before asking to publish and obtain approval to attach them under the boundaries above; reuse existing approval for those exact assets. Prepare useful visuals for both the conversation and the PR: use GitHub-compatible Markdown images or Mermaid in the PR, with captions and a short textual explanation. Cindy-only components need a portable equivalent. Image links must be durable and accessible to the repository's readers, not local paths or session-only references. If an asset cannot be shared, retain the explanation and state the omission instead of inserting a broken link.

1. **Ask once, unless the user already asked you to open it** (then go straight to step 2). When the work is done and verified and you are waiting for the user's go-ahead to publish, including when they said "not yet" or "let me look first", ask with the PR card instead of inviting confirmation in text when Cindy's GitHub plugin offers it: `ghost_call` with `ghost_id` `"cindy-github"`, `namespace` `null`, `tool` `"pr_card"` and args `repo`, `head`, `base`, plus `commits` and `files_total` from `git rev-list --count` and `git diff --name-only` against `origin/<base>` (count uncommitted changes too). The card does not need title or description fields; the explanation above belongs in the conversation. If this branch already has a card, update it with its `card_id` and the new counts rather than showing a second one. Keep the returned `card_id`, end your reply with one short line pointing at the card without saying where it is (Cindy places it at the end of your reply), and do not ask again in text. The user answers by clicking (a hidden message from the plugin arrives with the choice and the card's `settings`) or by saying so. Ask in one short sentence instead when the plugin is unavailable or the user is talking to you through an IM channel, where cards are not shown. Just ask; do not explain that this Skill or a rule makes you wait, and do not link this Skill or other local files.
2. Commit only related files, following the repository's rules. Run `node "<skill-dir>/scripts/pr-preflight.mjs" "<worktree>"` (add `--base <branch>` when the PR targets a branch other than the default one): fix every `BLOCK` (it checks only what the repository declares, such as DCO sign-off), handle each `WARN`, re-read the rule files it lists, and use the PR template it prints. Push the branch, then `gh pr create` (add `--draft` only when the user chose a draft; when reporting, mention the draft state only for a draft), adapting the explanation and useful, approved visuals above to the repository's PR template: what changed, how it was verified, risks. Write for reviewers who have not seen the conversation, and refresh the description and visuals if the final scope changed. Preserve the explanation when no template exists. Before reporting success, read back the published body and check that the intended text, diagrams and image references were carried over.
3. **Complete the follow-up handoff on every channel, including IM.** Card visibility only changes presentation, not whether saved preferences apply. When reporting a PR this task just successfully created, pass `published: true`. Omit this on ordinary lookups. Pass `following: false` if the user requested publication only or explicitly stopped follow-up. In Cindy, update the existing `pr_card` with `pr`, or create it with `repo` and `pr`, and read its `settings`; `disposition: "existing_task"` means another task is following this PR, so do not apply `auto_follow` or `auto_rename` here and keep the in-card link. For a PR in a group chat or an unrelated source task, read preferences first and put the card in the dedicated task described in `references/follow-up-setup.md`. In IM (or when card delivery fails), call `ghost_call` with `ghost_id: "cindy-github"`, `tool: "pr_follow_settings"`, `args: {}` to read the same preferences without showing a card. A settings read failure is unknown, never `auto_follow: false`; use an already-known explicit instruction if available, otherwise report the missing setting and offer following once in text. Do not repeat a failed card call just to obtain settings.
4. A card receipt with `follow_state` owns setup: `active` confirms the schedule is running, `paused` means the schedule still exists but is paused, `stopped` means it ended, and `failed` or `unverified` requires reporting the card’s reason. Do not create another schedule on these paths. Apply the user's explicit instructions first, then saved preferences. A prior explicit stop for this PR still wins; do not restart it on an ordinary update. `auto_follow: true` (when `follow_state` is absent) → `references/follow-up-setup.md`, without asking again (drafts still require the user's draft-follow preference or explicit request). `auto_rename: true` applies to the PR's own task, never to the originating group chat. Pass `follow_model` intact into the follow-up handoff. Only report `renamed` / `following` on the card after the corresponding action has succeeded.
5. **Close with the actual follow-up state alongside the PR link:** verified active (name the independent task if used), not enabled, setup pending, waiting for a decision, finished because the PR is merged/closed, or failed to start (reason and next step). A created task or a delivered handoff alone is not active follow-up. Do not end with only "waiting for CI/review". If no instruction or preference enables following, offer it once as described in `references/follow-up-setup.md`. Apply this same closure after updating a PR: recheck existing follow-up and do not silently leave a previously missed handoff unaddressed.
