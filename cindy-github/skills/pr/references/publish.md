# Starting Work and Opening a Pull Request

Read this when starting a change that will become a pull request or opening a PR (`SKILL.md` sections 1 and 2).

## 1. Start the work

For a change that will become a pull request (not for a question or a read-only investigation):

- **Already isolated:** if the task already works in a worktree or feature branch made for this same change, keep using it. A branch left over from another change does not count: create a task worktree instead of stacking unrelated commits on it. Fetch the target repository’s default branch and merge the fetched tip if the work branch is behind.
- **Otherwise create a task worktree:** call `cindy_helper` → `create_task_worktree` (category `control`; pass `repo_dir` when the task directory is not the repository itself). Cindy creates a branch from the freshly fetched remote default branch, binds the worktree to this task and removes it when the task is archived. The task itself does not move: run every shell command from the returned `worktree_path`, use absolute paths inside it for edits, and re-read the repository's rules there (the main checkout may be older). Keep using that path after restarts and context compaction. If the tool returns `base_fetched: false`, tell the user the base may be stale. Before opening the PR, successfully fetch its target branch from the target repository and merge the fetched tip. If fetching still fails, report that the base is still unverified.
- **Fallback** when the tool is unavailable or fails: fetch the default branch from the PR target repository (usually `upstream` in a fork checkout or `origin` otherwise). On success, run `git worktree add --no-track -b <branch> ../<repo-folder>-<slug> FETCH_HEAD` and work there. If fetching fails, report that the base is still unverified.

## 2. Open the pull request

**Task title:** whenever this workflow renames the PR’s own task or creates a dedicated follow-up task, use `#<number> <short topic>` (for example, `#1234 修复登录状态`). Summarize the core change in the user's language as a short phrase; preserve distinguishing technical names, but omit `PR`, workflow prefixes such as “Follow” / “跟进”, conventional-commit prefixes such as `fix:`, and redundant detail. Do not copy the full PR title or change the title on GitHub. Use `cindy_helper` `set_current_session_title` for an existing task only when automatic renaming is enabled or the user requests it.

**Explain the change before offering to publish.** Once the work is verified, give a concise, self-contained summary in the conversation before showing the PR card or asking in text. Lead with the problem and resulting behavior, then the main changes and verification results; mention material limitations when present. Use plain language and scale the detail to the change: a small fix may need only a few sentences. File names, diff statistics and a card alone do not explain what the PR does. Base the summary on the final diff, including related uncommitted work. If the user already asked to publish, give the same brief explanation and proceed without another approval round.

**Use visuals when they clarify the change.** A before/after screenshot can explain a UI change; a small diagram can explain a flow or interaction. Keep simple changes textual. Screenshots showing only simulator/emulator, mock, fixture, or redacted/sanitized data (with no real user, account, machine, or private/sensitive information) may be attached directly without asking first. When a screenshot contains real or unredacted user, account, machine, or private/sensitive data—or you are unsure it is clean—show it and wait for explicit approval before attaching or publishing (never push, open/update the PR, or post while waiting for the answer); reuse existing approval for those exact assets. Prepare useful visuals for both the conversation and the PR: use GitHub-compatible Markdown images or Mermaid in the PR, with captions and a short textual explanation. Cindy-only components need a portable equivalent. Image links must be durable and accessible to the repository's readers, not local paths or session-only references. If an asset cannot be shared, retain the explanation and state the omission instead of inserting a broken link.

1. **Ask once, unless the user already asked you to open it** (then go straight to step 2). When the work is done and verified and you are waiting for the user's go-ahead to publish, including when they said "not yet" or "let me look first", ask with the PR card instead of inviting confirmation in text when Cindy's GitHub plugin offers it: `ghost_call` with `ghost_id` `"cindy-github"`, `namespace` `null`, `tool` `"pr_card"` and args `repo`, `head`, `base`, plus `commits` and `files_total` from `git rev-list --count` and `git diff --name-only` against `origin/<base>` (count uncommitted changes too). The card does not need title or description fields; the explanation above belongs in the conversation. If this branch already has a card, update it with its `card_id` and the new counts rather than showing a second one. Keep the returned `card_id`. In Cindy, point to the card in one short line. If the current reply is going to X or another external chat, ask the same question once in plain text there; the card stays in the Cindy task. The user can click or answer in text. If the card is unavailable, ask in text.
2. Commit only related files, following the repository's rules. Run `node "<skill-dir>/scripts/pr-node.cjs" pr-preflight.mjs "<worktree>"` (add `--base <branch>` when the PR targets a branch other than the default one): fix every `BLOCK` (it checks only what the repository declares, such as DCO sign-off), handle each `WARN`, re-read the rule files it lists, and use the PR template it prints. Push the branch, then `gh pr create` (add `--draft` only when the user chose a draft; when reporting, mention the draft state only for a draft), adapting the explanation and useful visuals permitted above to the repository's PR template: what changed, how it was verified, risks. Write for reviewers who have not seen the conversation, and refresh the description and visuals if the final scope changed. Preserve the explanation when no template exists. Before reporting success, read back the published body and check that the intended text, diagrams and image references were carried over.
3. **Show the published PR in the originating Cindy task on every channel.** Call the GitHub plugin's `pr_card` with `repo`, `pr` and `published: true`, including when the user directly requested publication without an ask card. Reuse the task's `card_id` when available. This also applies to X and other IM requests and to subsequent messages typed directly in Cindy. A task's origin or title does not establish where the current message came from. External replies carry the PR link and follow-up status as text; the card belongs in Cindy. Apply an explicit publication-only request or stop with `following: false`. For an ordinary lookup omit `published`.
   - In a group or unrelated dispatcher that needs a separate follow-up task (the follow-up setup reference), show the source card with `published: false` instead. Read its preferences and hand off enabled or explicitly requested following to the dedicated task. Refresh the source card after the handoff to show the verified owner's link. An X/IM origin alone does not make a task a group or dispatcher.
   - Use the card receipt for preferences and follow-up state. For `disposition: "existing_task"`, keep the reference to the existing follower. Only fall back to `pr_follow_settings` when the card call failed to return preferences. Report card delivery failure separately, verify any existing schedule before recovery, and continue authorized follow-up under the follow-up setup reference. If the preference cannot be read it is unknown; use an explicit instruction when available, otherwise offer following once in text.
4. A card receipt with `legacy_hook_repair` identifies an existing, verified schedule and gives the replacement command; report the exact command and ask the user to change it in Automation settings without changing its timeout. The scheduler does not expose a caller-supplied conditional update, so do not automatically rewrite the hook or create another schedule. A card receipt with `follow_state` owns setup: `active` confirms the schedule is running, `paused` means the schedule still exists but is paused, `stopped` means it ended, and `failed` or `unverified` requires reporting the card’s reason. Do not create another schedule on these paths. Apply the user's explicit instructions first, then saved preferences. A prior explicit stop for this PR still wins; do not restart it on an ordinary update. `auto_follow: true` (when `follow_state` is absent) → `references/follow-up-setup.md`, without asking again (drafts still require the user's draft-follow preference or explicit request). `auto_rename: true` applies to the PR's own task, never to the originating group chat. Pass `follow_model` intact into the follow-up handoff. Only report `renamed` / `following` on the card after the corresponding action has succeeded.
5. **Close with the actual follow-up state alongside the PR link:** verified active (name the independent task if used), not enabled, setup pending, waiting for a decision, finished because the PR is merged/closed, or failed to start (reason and next step). A created task or a delivered handoff alone is not active follow-up. Do not end with only "waiting for CI/review". If no instruction or preference enables following, offer it once as described in `references/follow-up-setup.md`. Apply this same closure after updating a PR: recheck existing follow-up and do not silently leave a previously missed handoff unaddressed.
