# 设备模拟器性能重放

[English](simulator-performance.md)

## 范围与复跑

这是固定脚本的工具链对照，不是完整 Agent 任务评测，不能据此推算模型、
harness 或推理强度的端到端提速。原始历史、App 包、设备标识、存档和截图
仅保存在本地，不提交仓库。

基线为提交 `64bbaf3f253b3f118c2a0a40ee67020d945d94dd`、插件 `0.2.23`；
实测候选为已冻结在私有证据中的 `0.2.24` 源码。两版使用相同的随包原生运行时。
提交 PR 前，实现在 `b825436`（插件 `0.2.29`，截图方向与导出修复）上重新整理，
版本升为 `0.2.30`。下文统计仍是原来的 0.2.23/0.2.24 对照，不能当作
0.2.30 的测量；安装与构建校验代码不受这次基线更新影响。
Review 后续 `0.2.31` 在复用验证记录前增加确认扫描，受影响的性能另列于后文。
本 PR 没有改变依赖、权限、第三方平台授权、插件身份或发布配置。

`.tests/baguette/replay-worker.cjs` 加载各版本真实的 runtime 和 core，
只为两版同样替换本地状态根目录，不替换 Cindy 中已安装的插件。目录必须包含
`replay-only` 标记和专用模拟器集合，不能指向共享设备。故障模式只拦截 viewer
就绪或截图传输，App 启动和触摸仍真实执行，不注入 App 内部函数。故障结果与
正常延迟分开统计，不声称复现了历史原生库错误。

在版本控制外创建私有 JSON 配置，包含 `baseline`、`candidate`（插件源码
目录）、`root`、`udid`、`appPath`、`bundleId`、`output`。状态目录的
`runtime-settings.json` 使用 `{"enabled":true,"idleMinutes":0}`。
用本机已安装的运行时在 `root/devices` 创建新设备，并明确指定这个集合和
设备启动。测试前冻结 App 和完整文件内容清单，另保留可执行文件、资源和签名
资源指纹，用于核对历史构建。

在仓库根目录运行：

```sh
python3 .tests/baguette/performance-replay.py /private/replay/config.json --case install --first --rounds 3
python3 .tests/baguette/performance-replay.py /private/replay/config.json --case info --rounds 5
python3 .tests/baguette/performance-replay.py /private/replay/config.json --case install --rounds 3
python3 .tests/baguette/recovery-replay.py /private/replay/config.json --mode touch --rounds 5
python3 .tests/baguette/recovery-replay.py /private/replay/config.json --mode capture --rounds 5
python3 .tests/baguette/recovery-replay.py /private/replay/config.json --mode viewer --rounds 5
```

每组使用独立 `output`。恢复测试配置另需 `env`、`arguments`、`initialText`、
`targetText` 和 `tap` 对象。已恢复的运行中场景可配置 `keepRunning: true`、
核实过的 `appPid`、原生 `prepareSteps` / `cleanupSteps`，避免每轮激活或重启
App。仅准备动作明确因方向问题返回 `not_executed` 时，才在独立截图成功后重试
一次；测量中的输入不重试，失败记录不删除。依据历史构建和新截图确定输入，并在每次动作后验证
目标画面。`--first` 只卸载专用集合中指定的 App，其余用例不擦除设备。
轮次按 AB/BA 交替，准备步骤单独记录。没有清空操作系统缓存：首次安装表示
App 尚未安装，不表示存储冷缓存。重复 info 在每个 worker 初次完整校验后
保留验证记录；重复安装每轮先校验两版，因为旧版可能更换已安装容器。

## 校验约定

轻量元数据不证明构建一致。完整比较用 rsync 校验全包内容，同时比较可执行
文件身份，并独立比较符号链接目标，避免本机 openrsync dry-run 漏报链接变化。
验证记录只在当前 worker 内有效，最长一小时；每次复用都检查两个完整目录树
的路径、设备/inode、类型/权限、大小、纳秒 mtime/ctime 和链接目标。0.2.31
要求两次连续遍历两个完整目录树都与验证记录一致，从而检测第一次扫描中已经
访问过的资源随后发生的变化；发生变化就放弃复用。等长且
恢复原 mtime 的资源修改也会失效。完整校验期间有变化，不保存有效证明。
这依赖本机文件系统正常的变更语义，不证明 App 数据、运行内存或外部内容，
也不持续监控之后的写入。

安装和校验复用现有 job。阶段与耗时来自实际执行，不生成百分比。
状态查询建议等 85 秒，完成即返回，多设备可以并行等。比较失败保持未确认，
不能据此认定必须重装。输入确认完成后，观察使用独立的有限预算；恢复只观察，
不重发输入或重启已经启动的 App。既有方向、面板及未知执行状态保护保留。

## 实测结果

测试日期 2026-10-25：Mac Studio M5 Ultra、36 核、256 GB；macOS 27.0.1
`26A434`；Xcode 27.1 `27A9269`；专用 iPhone Air，iOS 27.0 `24A434`。
冻结历史游戏包为 6,759,470,259 字节、99,469 个文件。可执行文件、主要资源、
资源索引及签名资源指纹与历史记录一致，完整严格签名校验通过。

历史领奖场景通过临时存档的隔离副本恢复，再用真实摇杆移动和 NPC 对话进入，
没有注入驱动或调用 App 内部函数。重放的是历史奖励点击、观察参数和装备 Tips
验收目标。两版每次测量都从相同的未选择奖励面板开始；奖励名称、装备数值与
历史截图一致。场景准备和世界相机位置与历史注入式 fixture 不同，不声称完整
重放了当时的整个 Agent 会话。

计时包含真实插件 runtime、原生输入、文件截图、job 和 OCR 目标验证，不包含
Cindy 桥接/宿主页面渲染、模型附图传输或模型思考。准备与清理单独记录。
P90 使用 nearest-rank，小于十个样本时即最大值；小样本只描述这些实跑，
不代表总体性能保证。

两版脚本都使用 `wait=85` 查询状态，以区分运行时变化；不假设历史 `wait=1`
调用都对应一次模型往返。等待建议属于使用体验改进，不据此宣称模型提速。
首次安装计时截止于构建一致性确认；启动与可见场景验收另记在之后的原生场景
恢复和观察用例中。

viewer 故障用例使用已经运行的 App，明确调用 `launch(relaunch=false)`，
随后让 viewer 就绪在 12 秒后失败，验证保留该进程并取得画面；它不是冷启动
性能评测。截图故障发生在真实点击已确认之后的附带截图，两版随后都通过独立
截图及装备 Tips 目标验证恢复。

重复构建检查的中位数下降 96.9%，重复安装下降 96.7%；均限于已经完整验证且
验证记录仍有效的热态场景，首次完整验证仍然必要。这个历史包未声明可选的
`CFBundleSupportedPlatforms`，旧版会重新复制；新版允许在确认原生 iOS 包
内容未变后跳过。增量同步仍要求明确的原生平台元数据，Vision 兼容包仍整包安装。

首次安装和普通点击没有明显改善。截图超时恢复中位数下降 60.6%，包含成功的
后续截图及目标验证。点击调用本身从 42.41 秒降到 12.94 秒：旧版观察会尝试
两次截图，新版受限观察只尝试一次；两版之后都补一次独立截图。每次测量点击
只有一个原生输入信封，输入重试为 0；两个故障组均确认原 App PID 仍存活。

viewer 恢复没有延迟收益：中位数 20.28 → 20.61 秒，P90 20.62 → 34.22 秒。
新版把每轮一次截图纳入原调用，五轮测量调用由 15 次减到 10 次，没有自动重启
App。每个故障组、每版的五次预期观察失败都作为部分结果保留，没有抛成整次
工具失败；表中这些行失败调用为 0，不表示没有注入故障。

调用与准备累计包含失败尝试。等待为测量中 `install_status` / `wait_for` 的
墙钟耗时，包含校验、截图或 OCR，不是 CPU 空闲时间。新版首次安装的等待累计
更大，是因为完整校验在 job 内；旧版在 `info` 内同步阻塞。中位数/P90 只统计
完成目标的样本，失败率同时列出。首组普通点击在每轮准备中明确做一次不重启的
启动激活；追加组和最终故障组保持 App 运行，不做这次激活。

### 中断记录与剩余边界

第一台专用设备完成首装/info 和普通点击各五轮对照；后续探索性故障测试中，
跨新旧版本有四次准备尝试中断、五次失败调用，错误为画面几何或原生 display
binding 不可用。记录保留。关闭这台测试设备后，创建相同规格的第二台，安装
同一冻结构建；最终 viewer/capture 两组在第二台各完成每版五轮。

第二台追加普通点击每版完成三轮，但候选准备阶段中断两次（`SCREEN_UNAVAILABLE`、
`INPUT_FAILED`，均 `not_executed`）。一次独立截图用 4.58 秒恢复且 PID 不变，
随后取消已观察的奖励面板用 5.06 秒（额外两次调用，不在计时表中）。之后的
输入绑定失败没有重发输入，该系列结束。随后独立扩展验收的旧版准备也报告了
相同绑定失败。没有因果证据，不将这些失败归因于优化；本补丁也不能声称解决了
底层原生方向/画面绑定的间歇异常。

早期候选逐文件异步 stat 反而变慢；改成小批量遍历、批间让出执行后重新冻结并
重测，早期结果单独保留，不计作最终候选数据。最后的宿主路由修正让补截图跟随
实际设备并保留任务上下文；计时覆盖的后端文件未变。宿主行为有模拟回归，
没有真实宿主延迟证据。

Android、tvOS、Vision Pro 未做本次运行时性能对照。依赖、权限和宿主授权未变。
冻结 0.2.24 时，仓库要求的完整测试通过 623/623，官方打包器校验并生成
0.2.24。未替换共享 Cindy 的插件。

中断系列结束后，另行初始化专用设备做不计时的扩展验收。两版都从同一原生
存档恢复，通过奖励选择、盾牌 Tips 切换、取消后重置选择，以及单次领取后
进入下一任务页。设备初始化不算故障恢复。两个最初写错的 OCR 预期根据实际
画面纠正，失败断言保留在私有记录中；没有盲重发输入或注入 App 函数。
测试结束后，两台专用设备均已关闭。

## 提交 PR 时的 0.2.30 补验

整合主分支的截图方向/导出修复后，完整测试通过 635/635，官方打包器生成
0.2.30。在隔离 worker 中加载最终源码，使用相同专用设备、历史构建和原生
存档，各做一次画面验收：

- 普通奖励点击：正向截图显示选中的装备及 59 每秒伤害，原生触摸信封恰好一个。
- 选择盾牌后附图超时：输入已执行，截图尝试一次，观察阶段在 12.003 秒结束。
  独立截图显示选中的盾牌及 8 物理防御，没有重发输入，App PID 保持不变。
- viewer 失败：明确调用一次 `launch(relaunch=false)`，仍为原 PID；原调用的
  兜底截图显示同一盾牌 Tips，没有恢复性启动或终止 App。

这些是兼容性检查，不是新的 A/B 统计。固定恢复脚本最初在准备阶段中断：
`wait_for` 搜索 30 秒后返回 `met=false`、未识别到文字，但附带截图实际显示
正确奖励面板。失败尝试保留。之后先用独立截图确认当前状态，再单独进行画面
验收，不能把原来的自动断言失败改算成功。本 PR 不声称修复了文字等待可靠性。
补验后专用设备已关闭，没有操作共享设备或替换共享插件。

## Review 后续：0.2.31

复用验证记录前新增对两个完整目录树的第二次元数据遍历。回归在第一次扫描
已经访问资源后、扫描尚未结束时写入等长内容并恢复 mtime，要求 info 报告
不一致，install 进行同步而非跳过；源包与安装包两侧都覆盖。
Android 的 `until` 返回后，后续观察截止时间收紧为原调用截止时间与当前时间
加 12 秒的较小者，覆盖文字快速出现、等待较久和原截止时间更早三种情况。
完整测试通过 644/644，官方打包器生成 0.2.31。Android 证据为模拟回归；
Apple 的截图与 viewer 路径未受影响，沿用 0.2.30 的画面验收。

同一专用设备上重新尝试两次 0.2.23 基线，均在准备阶段因 checksum 比较未确认
而中断，分别为 110.079、110.020 秒。两次均未证明构建一致，不计入成功延迟
样本，也没有基于这些失败触发恢复性安装；原始记录保留。第二次已部分预热操作系统
缓存。这些失败不替代先前完成的 0.2.23/0.2.24 数据。

补充对照改用已提交的 0.2.30（`3716260`）与冻结的 0.2.31 候选，同一专用
设备、历史构建和未改动的重放脚本，用于单独量化确认扫描的成本；不能当作
最初优化前的基线。每个 worker 先完成完整校验，再按 AB/BA 交替测量，
不清空操作系统缓存。
