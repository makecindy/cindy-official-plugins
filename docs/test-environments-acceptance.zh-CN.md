## 准备一次，后面复用

1. 选一台控制机 A，在用于验收的 Cindy 宿主中导入上述 `.cindy`，启用插件，打开管理页。
   优先用专门的验收宿主，避免把未完成插件混入日常工作。**插件装在控制流程的宿主里，
   它启动的目标开发版 Cindy 不再安装本插件来启动下一层。** 记录宿主版本、渠道、系统与插件版本。
2. 准备一份可构建的目标应用源码。Cindy 项目需有现有 restart 协调器和工具链，
   包括 Node、项目包管理器、macOS 上的 Python 3 和 lsof；SSH 目标需 Node 22+、Git。
   缺工具时先补环境，不用反复点启动代替排查。
3. 准备两个你有权使用的正式账号，以下叫**账号甲、账号乙**；电脑叫 A、B，避免混淆。
   密码、验证码、扫码只在应用原有登录界面完成，不填进插件字段或聊天。
   日常宿主已登录不代表新的隔离目标已登录；插件不扫描或搬运日常宿主的历史登录。
4. 让 Cindy 配置一个项目和固定桌面方案，可直接复制：

   > 用 Test Environments 保存项目，路径是【源码绝对路径】，接入方式 cindy。创建方案 qa309-desktop，
   > 启动方式 acceptance，平台 desktop，隔离名 qa309-main，调试端口选一个未占用的，
   > 远程被控和后台自动触发关闭。先返回计划，不启动、不读取凭证。

   预期：能看到源码路径、稳定隔离名、调试端口、账号尚未选择、五步工作流。
   方案后续始终使用同一隔离名、区域与本机数据位置；不靠换一个空档案“解决”登录丢失。
5. 准备与本次业务对应的样本和用例。`fixture` 只是样本说明，不会自动造数据。
   `prepare`/`verify` 必须使用项目真实已有的参数数组命令，不能臆造客户端参数。
   未配置命令时，让 Cindy 用实际应用工具准备/检查样本并记录证据；不存在按钮或返回
   ACTION_NOT_CONFIGURED 不代表业务已经通过。若本轮要求命令化验收，先配置命令再测。
6. 全程记录 jobId；SSH 另记录 runId。首次构建可能安装依赖，要看进度日志。
   如果出现 STARTUP_TIMEOUT，记录阶段和耗时，停止并排查；不要留下旧实例后重复启动。

## 本机必须验收

### L1：实际安装、管理页与 AI 入口

1. 在管理页依次打开项目、账号、启动方案、用例、运行记录；添加项目、保存方案、刷新页面。
2. 让 Cindy 读取插件 catalog，并预览 qa309-desktop 的 plan。
3. 修改方案展示名、保存，关闭并重新打开管理页，再让 Cindy 读取 catalog。

**预期：** 页面与 AI 看到同一份目录；保存后重新打开仍存在；无空白页、持续连接失败或未知工具；
方案的隔离名、区域、账号引用不会因改展示名改变。记录宿主版本和页面截图。

### L2：首次正常登录、自动记住全部账号

1. 点击“启动”一次，保存 jobId，查看运行记录/让 Cindy 查询 status。
2. 目标应用要求登录时，在目标应用正常登录账号甲。按应用正常入口添加并登录账号乙。
3. 回插件刷新账号页；必要时点运行记录的“记住账号”刷新公开引用。
4. 让 Cindy 返回当前目标实例的登录状态、当前账号、账号目录 ID、档案位置和联网核验结果。

**预期：** 未登录时等待用户，不假报 ready；甲、乙都能被记住，不只记当前账号。
密码/令牌不出现在插件表单、工具返回或目录中。只有实际身份明确、联网校验成功、数据库可用后，
状态才是 ready / application-account-online。账号出现在列表中本身不等于登录仍有效。
**记录：** jobId、两个目录 ID、profile/isolated、userDataDir、状态截图；不记录凭证。

### L3：甲 → 乙 → 甲，以及样本隔离

1. 在账号甲创建一个可识别的测试样本，例如 `QA309-甲-日期`；记下它在应用里的位置。
2. 在运行记录下拉框选择账号乙并点“选用账号”，等身份与联网核验完成，再在目标应用核对头像/账号。
3. 检查甲的私人账号数据不被当成乙的数据；在乙创建 `QA309-乙-日期`。
4. 选回甲，等重新核验，确认甲样本仍在、乙样本没有串成甲的私人数据。

**预期：** 查询和实际界面身份一致；切换期间不继续显示旧的 ready 作为新账号证据；
两个账号的预期账号私有数据分开。应用本来支持共享的数据按业务规则判断，不能要求所有内容都不同。
命令退出 0、窗口打开都不能替代账号核对。截图分别标明甲/乙，分享时遮蔽私人内容。

### L4：停止、重启及插件重新启用不丢本机登录

1. 停止这次 job，查询至 stopped，确认只关闭目标测试实例，日常宿主及其他应用仍正常。
2. 用同一方案、隔离名、区域再次启动。不要复制任何凭证文件，也不要重新造一个空档案。
3. 查看两个账号引用是否都在，切到甲/乙各核验一次，检查先前创建的样本。
4. 再停目标实例，停用并重新启用插件，重新打开管理页、启动同一方案。

**预期：** 未失效的应用本机登录可复用；账号引用、档案和样本保留。
重新启用不是“真实版本升级”证据；有下一版包时再补原位升级测试，本次不要求降级到旧包。
如果出现系统凭证库授权弹窗，由你正常确认并记录，不当作插件已绕过系统保护。

### L5：登录失效时明确等待重新授权

1. 在测试档案中先完成一次 ready，然后通过应用正常入口退出当前测试账号；
   或使用应用支持的本设备会话撤销。不要手工删除钥匙串、复制凭证或改认证数据库。
2. 刷新运行记录，让 Cindy 返回状态。若应用退出会同时关闭窗口，重新启动同一方案观察。
3. 按提示在目标应用重新登录，再查询身份、联网校验和样本。

**预期：** 不继续假报已认证；已核验会话失效显示重新登录提示和 ACCOUNT_REAUTH_REQUIRED，
全新未登录/已移除账号也可能是 ACCOUNT_SIGN_IN_REQUIRED；等待正常授权，不反复自动切换。
重新登录后可恢复使用。保留两张状态截图：失效后、恢复后。
应用服务端若有全设备撤销策略，要记录该策略，不能把服务端全局撤销一概当成插件搬运登录态。

### L6：用实际样本验一个真实业务用例，先截图再停止

1. 选定实际待验 PR 的一个可操作用例，写下动作和预期。例如“切换账号后仍显示本账号样本”。
2. 通过“准备样本”执行项目 prepare，或让 Cindy 用实际应用工具准备命名样本。
3. 执行项目 verify，并在目标应用实际操作该用例；记录命令结果和可见业务结果，两者分开。
4. 在目标应用仍运行时，让 Cindy 对当前 job 做 inspect，并请求截图。
5. 确认截图是这个目标实例及正确账号的内容，再停止并查询至 stopped。

**预期：** 配置 prepare 后桌面有“准备样本”；命令失败或业务不符如实失败。
截图来自目标实例，不是日常宿主或旧图片；只保存为本机私有证据。
**截图必须在停止前取；停止后截图明确不可用，但日志和状态仍可读取。**

## 第二台电脑与真实 SSH 必须验收

### R0：B 的一次性准备

1. 选择准确的 B（型号/系统符合目标），准备当前用户的 SSH 访问和已核对的主机信任。
   Git 需能从 B 自己访问目标仓库；不会转发 A 的 SSH agent 来代替 B 的 Git 权限。
2. 在 B 配好目标源码和工具链。用同版本插件的独立 CLI或 B 的验收宿主建立本机目录和方案；
   **只在 A 装插件不会自动给空白 B 建好目录。** B 的路径和账号目录 ID以 B 返回值为准。
   一种可直接操作的准备方式是在 B 的验收宿主导入同包，重复本单 L1/L2 的项目、方案和首次登录；
   之后由 A 编排，B 的目标开发应用本身不再安装本插件。
3. 在 B 同一持久隔离档案正常登录账号甲（与 A 同一正式身份）；需要切换时也添加账号乙。
   在 B 完成一次本机 ready，然后停止该实例，释放端口及档案占用。
4. 不把 A 的登录档案、Cookie、钥匙串或 token 复制到 B。

**预期：** A/B 能各自正常登录同一正式账号；B 有自己的本机登录和公开目录引用。
B 未登录时正常等待登录，不要求 A 为它完成尚未实现的跨设备首次授权。

### R1：指定 B、指定 PR 预览，不误动原工作区

可复制给 A 上的 Cindy：

> 用 Test Environments 的 remote 工具读取【B 的 SSH 别名】的 catalog，必要时指定 B 的 Node 绝对路径。
> 列出实际型号、项目及方案，选择【B 方案 ID】。用 GitHub 工具读取【目标应用仓库】PR【编号】的最新 head SHA，
> 生成 remote plan，先展示目标、origin、精确 SHA、档案、准备/验证命令和人工/设备待办，不启动。

**注意：** #309 是插件自己的 PR；远端要构建哪个应用，就传那个应用仓库的 PR。
`pr.repo` 必须匹配 B 已保存项目的 origin，不默认把插件仓库当客户端仓库。

**预期：** 型号/电脑/路径正确，plan 返回唯一 runId，execution 为 not_executed；
没有新应用实例，原工作区与未提交文件不改变。记录 runId 和精确 SHA。
换另一台电脑时只换 target 和其本机方案，不重写整套业务模板。

### R2：真实检出、构建、复用 B 的本机登录

1. 确认 R1 后让 Cindy 对原 runId 调 start 一次；以后始终用这个 runId 查询。
2. 核对 actualCommit 等于预览 SHA，checkout 是新的独立工作树，B 原工作区仍完好。
3. 检查 B 的实际应用界面、账号甲及联网核验；再用返回的 B 账号目录 ID 切到乙、切回甲。

**预期：** 真正构建启动，不靠旧实例冒充；B 已有未失效登录可复用；账号、截图、状态属于 B。
B 缺少登录则等待你在 B 正常登录，而不是复制 A 的凭证。A 上的宿主/目标实例不被误停。
若 B 工具链、Git 权限或图形会话缺失，记录为环境问题，不记通过。

### R3：样本、真实用例、截图和证据回 A

1. 让 Cindy 通过 remote action 执行已配置 prepare，在 B 核对样本；再执行 verify 和真实用例。
   尚未配命令就先配置项目已有脚本，不能把 ACTION_NOT_CONFIGURED 算成功。
2. B 仍运行且身份已确认时，remote collect 请求 logs 和 screenshot，outputDir 指向 A 当前任务的绝对目录。
3. 在 A 打开返回的文件，核对截图内容、PR/SHA、runId、B 型号、账号及动作结果；检查文件摘要。
4. remote stop 后继续查至 stopped。再 collect 日志和结果，此时 screenshot 设 false。

**预期：** 停止前的截图与停止后的最终结果分开保存，各次 collect 有独立目录，不混入旧截图。
A 能打开实际文件，结果保留失败动作；human/device-tool 项仍是 pending，不能因脚本成功自动通过。
不会取回凭证目录，也不会自动把私人日志/截图上传 PR。

### R4：真实连接中断与恢复

1. B 已启动且记录原 runId 后，在可中断的测试网络暂时断开 A→B 的连接；先不要再启动或再发样本命令。
2. 查询原 runId，记录实际连接错误/超时。若恰好在 start/action/stop 回执阶段断线，状态可能 unknown。
3. 恢复连接，第一件事是查原 runId，核实 B 是否仍在构建/运行、动作是否已执行、停止是否已完成。
4. 明确实际状态后再继续剩余步骤。不要生成新 runId 或盲目重发已执行动作。

**预期：** 能恢复查看同一次任务，未重复创建实例或样本；未知不会被伪称“未执行”。
仅在状态查询时断线不能算“动作回执丢失”的真实验证，后者本轮已有故障注入覆盖；实机记录需写明断线时点。
不方便中断网络就保留该项待验，不把回环测试当成真实网络恢复已通过。

## 仅在实际需求涉及这些硬件时追加

- **实体手机：** 用 B 上可用的设备工具先列设备，核对准确 deviceId、型号、系统、构建版本，
  安装/启动后执行实际用例。模拟器不冒充实体手机；A 的本地设备工具不能自动算 B 的设备工具。
- **触控板：** 在目标开发版的真实任务侧栏，由真人完成缩放、连续反向、旋转、平移，
  分别记是否跳变/方向错误/手感异常。独立窗口或合成事件不代替真人侧栏证据。
- **平台兼容：** 本轮自动证据来自 macOS。Windows 账号监管明确不支持；Linux、移动端与
  最低声明 Cindy 版本需分别有真实环境证据，不要求你把 macOS 结果外推为其他平台通过。

## 维护者复现自动检查（不需要验收者重复跑）

在仓库外准备 Playwright Core 1.65.0、ssh2 1.17.0 和测试 Chromium。
将 1.1.3 包解压到独立临时目录，仅用于检查，不安装宿主；TEST_ENVIRONMENTS_RUNTIME 指向该目录。
以下路径需换成实际绝对路径。证据目录不得放入插件源码包。

```sh
TEST_ENVIRONMENTS_PLAYWRIGHT=/absolute/test-tools/node_modules/playwright-core \
TEST_ENVIRONMENTS_SSH2=/absolute/test-tools/node_modules/ssh2 \
TEST_ENVIRONMENTS_PACKAGE=/absolute/test-environments-1.1.3.cindy \
TEST_ENVIRONMENTS_RUNTIME=/absolute/unpacked-plugin \
TEST_ENVIRONMENTS_SSH_EVIDENCE=/absolute/private-evidence \
node --test .tests/plugin-contract.test.mjs .tests/localization.test.mjs .tests/provisioning.test.mjs .tests/publish-workflows.test.mjs .tests/test-environments.test.mjs .tests/test-environments-ssh.test.mjs .tests/test-environments-package.test.mjs .tests/test-environments.browser.test.mjs .tests/test-environments-ssh-loopback.test.cjs
```

浏览器默认使用 macOS 的测试 Chrome 路径，可通过 TEST_ENVIRONMENTS_CHROMIUM 覆盖；
可用 TEST_ENVIRONMENTS_BROWSER_EVIDENCE 指定页面截图目录。
SSH 回环只使用临时生成的测试密钥/主机信任和 loopback 服务，退出清理，不使用真实账号凭证。
遵守本机测试资源队列，不绕过限流，也不把等待资源写成测试通过。
