# 账号选择与两种 SSO：需求、用法和未完成项

[English](test-environments-accounts.md)

2026-11-09 用户确认：**日常 Cindy 已登录的企业账号、浏览器已有的企业 SSO，两种都要**；
同时可添加并选择邮箱、手机号等 Cindy 实际支持的正式账号。统一跟踪在 #309。
这是确认后的完整目标，不代表 1.2.1 已实现所有授权入口。

## 最终应该怎么用

1. 选择要测试的项目。
2. 从已保存账号中选本次要用的账号；没有时选择添加账号。
3. 新增账号选择以下入口之一：使用本机日常 Cindy 账号、通过浏览器 SSO 授权、
   或到 Cindy 原有登录页使用邮箱/手机号等已启用的方式。
4. 正常完成必要授权，看到正确账号后启动/继续这次测试；以后可选择保存的账号复用。
5. 停止后档案保留；登录失效则只提示该账号重新授权，不自动改用其他账号。

SSO、邮箱、手机是登录入口，不一定是不同身份。同一正式账号通过不同入口登录时，
使用应用返回的账号编号去重，不按邮箱域名、组织类型或显示名猜测登录方式。
同一身份的个人/组织成员账号仍按应用返回的不同编号分别选择。
账号选择不等于选择密码；密码、验证码、令牌不得填进插件或交给 AI。

## 1.2.1 到底可以做什么

| 入口 | 当前实际情况 | 还缺什么 |
| --- | --- | --- |
| 选择测试档案里已保存的账号 | 启动前选择下次账号；运行中可切换；按目标应用返回的账号编号保存引用 | 真实账号/宿主集成证据；当前列表只显示应用提供的名称，不保证显示登录方式 |
| 邮箱/手机号新增账号 | 在目标 Cindy 原有登录界面手动操作，插件发现并保存公开引用 | 插件尚无独立“添加账号”一键入口；手机登录依区域及服务配置，不保证每个渠道开启 |
| 浏览器已有 SSO | 目标 Cindy 原有 SSO 流程打开系统浏览器；可能复用浏览器已有企业会话 | 仍需按组织/浏览器要求选择和确认，不能保证免输密码；真实 SSO 联调未完成 |
| 日常 Cindy 已登录账号直接授权测试实例 | **尚未实现**，当前仅发现目标实例自己的账号 | 缺少经用户确认、绑定目标实例并签发独立会话的完整公开授权接口 |

“本机”不代表两个隔离档案共用登录态。日常 Cindy 的登录仍由日常 Cindy 保存，
测试实例的登录由测试实例保存。不得把日常凭证库挂到测试实例、解除隔离或复制文件来冒充授权。
SSH B 上的系统浏览器也不是 A 的浏览器；远程首次登录链接交接仍未实现。

## 现在可以逐项验什么

1. 在测试实例正常登录账号甲，回插件更新状态；应发现甲。
2. 停止实例；从“下次启动使用的账号”选甲，再启动；有效登录应复用原档案，不需重新输入密码。
3. 使用目标应用原有入口添加账号乙（可为另一登录方式），更新插件；应同时保留甲、乙。
4. 运行中在“切换账号”选乙，再选甲；目标应用实际身份和数据应相应切换。
5. 如果目标 Cindy 登录页提供 SSO，在目标应用选择企业入口，按系统浏览器提示完成授权；
   验证新账号进入测试档案、可被插件选择，重启后仍可复用。不要把浏览器恰好免密当成日常 Cindy 授权。
6. 如果提供手机号入口，完成正常验证码登录，重复保存/选择/重启测试；无该入口时记“当前渠道未开放”，不伪造通过。
7. 日常 Cindy 已登录、测试档案未登录的直接授权项，当前记“未实现”，不能因步骤 5 成功改成通过。

账号档案路径和保存规则见[最简使用](test-environments-simple.zh-CN.md)与[方案交接](test-environments-handoff.md)。
插件配置默认位于 macOS 的 `~/Library/Application Support/Test Environments/catalog.json`；
账号的 `sessions[配置编号].userDataDir` 指向对应测试实例数据目录，凭证由应用保存在其 `safe-storage/`。
只查看路径/目录是否存在，不打开、解密或外发凭证文件。

## 日常 Cindy 授权的最小能力设计（未实现）

必须复用主程序的账号选择、用户确认、设备/实例身份与既有凭证库。插件仅编排和保存公开引用。

- 目标实例在主进程创建授权请求，绑定自己的实例/设备、区域、单次挑战、时效和账号目标；秘密留在目标主进程。
- 日常 Cindy 用原生账号选择器让用户明确选择账号并确认目标；显示可核实的实例/设备信息，不默认授权当前账号。
- 服务端验证授权方身份及目标挑战，允许/拒绝/过期可区分；为目标签发自己的会话，支持单次兑换、防重放和撤销。
- 目标主进程直接兑换并通过既有登录完成路径加密保存；插件只得到请求编号、进度和公开账号摘要。
- 取消/超时/断线后读取原请求状态，不自动重新批准、重复兑换或切到另一个账号。

当前核查的 auth-server 路由有正常验证码、浏览器授权码/PKCE 兑换、刷新和账号切换，
但未发现可直接复用的上述完整宿主→隔离实例授权链路；这不是“绝对没有任何相关代码”的断言。
当前宿主 accounts.settings 工具未暴露操作，插件 SDK 也未发现对应公开入口。
`authBeginAddAccount` 只初始化目标应用的登录状态，不等于替插件打开原生添加账号页面，
更不代表已授权。需要先补最小客户端/服务端契约与联调，不引入未经核实的端点。

本次记录已确认目标与缺口，未改客户端/服务端、未新增授权权限、未实现新登录入口。
