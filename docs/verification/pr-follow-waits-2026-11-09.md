# PR 跟进等待机制：历史场景回放（2026-11-09）

目标：出现可处理的新情况时及时恢复；已确认需要等待的事项不因无关主干更新反复唤醒模型。
方案与 CLI 契约见 [follow-up.md](../../cindy-github/skills/pr/references/follow-up.md#model-directed-waits)。

  回放使用合成的相同状态转换，不复制真实用户数据，也不把该任务中的安全判断当作已核实结论。

## 实现决策

模型在一轮结束时记录等待原因、具体检查/线程与下次有用的复查时间。记录与提交、检查运行
及线程状态绑定，保存在现有 gate 状态中；没有新增调度器、后台进程或宿主能力。

- 等人工：只有所有失败与未解决线程均已核查，且明确需要人工时，才允许不设到期时间。
- 等基线修复：模型选择有限时间，期间主干更新合并到到期那轮处理；仍必须合入修复、推送并确认新 CI。
- 等 CI 或临时依赖：模型选择有限时间，CI 结果或真正的新事件可以提前唤醒。
- 新提交清除旧等待，保留推送后评审收齐；新反馈、失败、冲突、队列问题、草稿转换、合并/关闭不被等待吞掉。
- 指定检查/线程每五分钟完整核对；未指定对象的等待用轻量探测。宿主状态触发可提前检查，但不能绕过等待筛选。
- 到期唤醒保留 pending/ack 与退避恢复；模型崩溃不能让到期任务丢失。无变化不反复发聊天总结。

基线修复尚未被确认时，脚本不能仅凭主干提交判断修复是否相关；因此它按模型选择的期限复查，
这是有意保留的延迟边界。新失败/评审等独立事件不受该期限限制。

## 场景与结果

| 场景 | 验证结果 |
|---|---|
| 等人工时主干更新、宿主提前触发、超过一天 | 继续等待，不唤醒模型、不每日催促 |
| 主干也失败，等待修复 | 到模型选择的期限复查；模拟合入后新 head 的 CI 通过仍唤醒一次 |
| 未设置等待的原有基线失败 | 原 `base-moved` 恢复路径仍有效 |
| 新的失败检查、人工技术反馈、机器人技术反馈 | 检查发现后立即放行 |
| 分支冲突、合并队列移除、草稿转换 | 立即放行；新冲突也不被机器人收齐窗口拖住 |
| 批准变化、指定线程解决 | 等待条件变化，放行重新判断 |
| 非必需检查从失败变通过 | 即使必需检查早已全绿，也能解除等待并放行 |
| 同名检查重跑后仍失败，汇总计数相同 | 按具体运行识别，下一次五分钟检查发现，不拖到三十分钟 |
| 重跑刚启动，结果未出 | 不唤醒；结果完成后放行 |
| 新的 head、自己的推送 | 旧等待失效；推送本身不唤醒，机器人反馈继续最多收齐二十分钟 |
| 不同 workflow 的同名检查 | 目标必须明确；未被等待覆盖的失败仍保留主干观察 |
| 旧等待到期，模型未启动/崩溃 | 重试与退避；无关主干更新不能不断重置到期重试 |
| 重试退避期间出现真正的新失败/新结果 | 可提前唤醒，不被旧故障的退避压住 |
| 慢任务确认时又来了新提交/同 head 新失败 | 只确认最早交付的观察，后来的事项不被吞掉 |
| 不完整快照、检查不可读 | 不当作“仍在等待”，放行调查且不越过未知事件 |
| 机器人编辑旧状态评论、自己的回复 | 不唤醒 |
| 旧 CI 记录被重跑替代、API 故障/限流、软链接入口 | 既有回归全部通过 |
| 错误 head、未知/歧义目标、未涵盖阻塞、无效时间 | 写状态与 ack 前拒绝，可修正后重试 |
| 真实 CLI 子进程读取等待文件 | 回执与状态正确，下一次无关主干变化退出码为 2 |

## 收尾衔接与指令精简（2026-11-10）

实际跟进暴露了回放假设：旧任务仍用普通 `--ack` 结束，虽然口头报告等待，状态中却没有
`wait`。原回放主动提供等待计划，只证明计划生效后的行为，不能证明任务会采用它。

收尾现在只分三种：有阻塞用 `--wait`，处理或推送后用带原因的 `--resume`，无阻塞和等待
时用 `--ack`。普通 ack 不能确认已知阻塞、未知数据或抹掉已有等待；先拒绝且保持状态原样，
在当前调用给出修正提示。`--resume` 明确清除等待及旧 defer 计时器，仍只确认最早交付的观察。
没有新增调度、迁移唤醒或重试机制，也不会从“CI 红”自动推断无限期等人工。

后台指令从 1,293 个空白分隔单词缩为 434 个；类型、时间范围及特殊情况统一放在参考文档。
每次实际放行只附一行收尾提示，skip 不附提示。收尾原因是模型对处理情况的声明，脚本只能
校验结构和范围，不能证明修复正确或保证模型总能选对等待类型。
