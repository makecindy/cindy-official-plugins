# 官方插件审查与合并规则（单一事实源）

> 本文件供 Greptile、Codex、自动合并流程与维护者共同使用。安全红线结构化条目见
> `.greptile/config.json`，插件归属见 `.github/plugin-owners.json`。
>
> 国内推包逻辑保持移除；合入 `main` 后自动向 Global Plugin Platform 提交 **待审包**
> （审核通过后才对用户可见）。合并与上架是两个阶段，合并门禁聚焦**真实代码与安全风险**，
> 不再把流程表单或实机自述当作合并阻断。

## 1. 三条核心底线与分级放行

只有三条真正阻断合并的底线：
1. **安全与权限红线**：无硬编码密钥、凭证仅走宿主托管注入、无未声明自主联网或命令注入、不可逆副作用不把不确定态误判为可盲目重试、无未经确认的权限/信任边界扩大或删改已发布插件 ID。
2. **CI 确定性检查全绿**：DCO、Manifest 与打包契约、四语言资源、改动插件单测、`plugin.cindy` 试打包。AI 审查不重复检查 CI 已校验的字段（版本号、SemVer、description 长度、四语言结构等）。
3. **无确认的 P0/P1 代码缺陷**：仅阻断有明确触发路径的安全问题、数据损坏、崩溃或核心主路径回归。

**明确退出合并硬门禁的项目：**
- ❌ **不把「实机测试证据」作为合并门禁**。单测 + CI 试打包 + 双机器人审查即满足合并要求；不要求固定实机勾选、也不因缺少真机运行记录阻止合并。真机与发布质量由上架审核及灰度兜底。
- ❌ **不因 P2 建议、风格偏好、措辞差异或低概率理论假设阻断合并**。

### 分级放行矩阵（L1 / L2 / L3）

| 级别 | 变更范围 | 放行规则 |
| --- | --- | --- |
| **L1 常规迭代（快车道）** | 已有插件的 bugfix、性能优化、小功能增强、UI/文案/多语言/图标、测试、可追溯的依赖维护；尤其是由 `.github/plugin-owners.json` 中的维护者或插件 Owner 更新自己的插件且未扩大边界 | **CI 全绿 + Greptile APPROVED + Codex 无未解决 P0/P1 → 直接可合**，不做额外人工复审，不卡实机验收 |
| **L2 边界变更** | 新增官方插件、`provisioning.json` 扩大到 `all`、新增/扩大权限/凭证/自主域名/子进程边界、变更第三方 OAuth scope 或依赖未就绪的宿主授权 | L1 条件 + 维护者只核对边界是否合理（新插件符合下方准入标准即通过，不重做代码挑刺）；未获平台批准或宿主未发布的 OAuth 授权标「等平台批准」暂缓合并 |
| **L3 仓库基座** | `.github/workflows/**`、`.greptile/**`、`AGENTS.md`、`.github/plugin-owners.json`、削弱 `.tests/` 门禁、重命名或删除已发布插件 | L1 条件 + 维护者明确 Approve |

> **合并授权纪律**：reviewer 身份本身不授予 merge/close 权限；已获维护者授权的合并程序在满足对应级别条件后可直接合并，不绕过 GitHub ruleset。

## 2. 双机器人分工与 AI 审查防熔断

- **Greptile**：安全红线与边界守门员，负责产出可自动合并的 `APPROVED`（L3 路径除外）。
- **Codex**：P0/P1 代码逻辑审查员。**只对确认的 P0/P1 发 inline comment**；P2 建议、边缘假设与代码风格不得以阻塞性 thread 提出，也不审查实机验收或版本安排。

### 防熔断纪律（防止 AI 审 AI 陷入死循环）

1. **2–3 轮收敛上限**：首轮集中指出真正的 P0/P1；后续轮次只核验「上轮 P0/P1 是否修复 + 本次修改本身是否引入新崩溃或安全洞」。**禁止在复审阶段持续发散新 P2，禁止对开发者为满足上轮 review 而新增的防御/兜底代码循环挑刺。**
2. **超过 3 轮触发熔断**：若同一 PR 超过 3 轮仍未收敛，停止继续往返——无新 P0/P1 则直接放行，确有分歧转维护者一次拍板，边缘改进另开 follow-up。
3. **用户体验优先**：不要因为极低概率的边缘配置或假设性竞态，阻塞正在修复主线问题的重要 PR。
4. **向后兼容按 `audience` 分层**：对照 `provisioning.json`：
   - **自选/早期插件（`audience` 非 `"all"`）**：不强求多代本地缓存、旧任务状态或历史记录的无缝迁移，允许在格式变化时干净重置或清晰降级。
   - **全员内置插件（`audience: "all"`）**：仅对用户持久数据、凭证和核心主流程要求向后兼容；非关键本地缓存同样不强求复杂多代迁移。

## 3. 设计与代码契约（精简）

- **授权跟随执行者**：工具调用内的普通 HTTPS / workdir 操作经 `callId` 复用既有 Agent 授权，CLI 走已有 Node worker，不得仅为预登记具体命令/域名新增声明；脱离调用的自主能力（Panel/订阅/scheduler/常驻进程）与随包 `node` Runtime 须在 `ghost.json` 直接声明。
- **契约一致性**：`ghost.json` tool `description`、`skills/**/SKILL.md`、settings 提示文案与四语言 `locales/` 若出现会导致误外发、计费或功能失效的**语义矛盾**才按 P1 指出；纯措辞润色不报。`docs/localization.md` 允许 settings 自渲染文案回退英文，缺 ja/ko 本身不是缺陷。
- **弱随机禁止**：发往外部服务的 id/nonce/state/boundary 使用 `crypto.getRandomValues` 或 Node `crypto`，不用 `Math.random` / 时间戳拼接。
- **错误信息可行动**：面向用户的核心报错（如 401/403/配置错）给出可操作提示，避免裸堆栈或 `error: undefined`。
- **已接受限制（勿再报）**：`.tests/localization.test.mjs` 的 `stripJsComments` 不解析正则字面量内的 `//`（扫描方向 fail-closed，零漏放风险，已确认接受）。

## 4. 新插件准入、受众与查重

新增插件、新增内置供应商或调整 `provisioning.json` 受众时，按以下三条直接判定（符合标准即通过，无需事先提案或额外产品批复；不符合则列明违反哪一条）：

1. **`all`（全员内置）**：多数用户受益、开箱即用无需自备第三方密钥或账号、不绑定个人或单团队流程、质量稳定。热度或投稿数量本身不构成 `all` 理由。
2. **自选接受（`{ "emails": [] }`）**：有用但小众，或需要用户自备密钥/账号。拿不准但有用时默认按自选接受。
3. **不予接受**：纯个人私有流程、纯示例/演示（改放 `docs/`），或 Agent 不装插件即可直接完成的能力。

- `ghost.json.author` 须为真实作者，不得冒充官方团队。
- **功能查重**：同一服务商的不同产品（Gmail/Drive/Calendar）与同一协议的不同服务商（163/iCloud/QQ/Yahoo）属合理共存；明显重复的通用能力（如又一个通用网页搜索）列出重叠插件并要求说明差异化定位。

## 5. 第三方 OAuth 授权（仅涉及时适用）

仅当 PR 新增/变更插件 `oauth.scopes`，或依赖有变化/尚未就绪的 Cindy 宿主 OAuth 授权时：
- PR 说明写清涉及的 scope、平台审核状态及（若用到宿主授权）宿主是否已发布。
- 未获平台批准或宿主未发布时，在 summary 单列「等平台批准」并暂停自动批准（不标代码 P1，不让 review check 失败）。
- 未涉及此类授权的 PR 完全跳过本节，不提要求。

## 6. 回复语言与摘要格式

- 始终使用 PR 作者的主语言回复（中文作者用简体中文，其余或不确定用英文）。
- 仅当存在经核实且未解决的 P0/P1 时在 summary 列出阻断项；无 P0/P1 时直接放行，不在摘要里附带“需补充实机验证”之类的伪阻断要求。
