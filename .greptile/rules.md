# 官方插件审查规则（review 契约正本）

> 本文件供自动 review（Greptile 等）与人工 reviewer 共同使用。安全红线类规则以
> `.greptile/config.json` 的结构化条目为准（带 severity），本文件补充设计标准、
> 流程纪律与判定口径。国内推包逻辑保持移除，合入 `main` 后自动向海外 Plugin
> Platform 提交变更包，审核通过后才对用户可见。阻断基于可核查的行为、影响和证据；
> 文件路径、审查分数、流程待办不能代替风险判断。

## 审查、决定与合并

- **代码问题**：说明触发条件、受影响行为和代码/协议依据。P0/P1 按实际安全、数据或
  功能影响判断；普通措辞、偏好和无证据假设不阻断，不要求作者为得到满分反复改码。
- **待验证**：说明缺少哪个受影响场景的证据、谁可以补。验收不足可阻止合并，但不
  自动成为代码 P1；技术 CI 不检查人工勾选，绿色 CI 也不证明实测完成。
- **准入与受众**：新插件、新供应商和 audience 变更（含扩大到 `all`）按
  「插件准入与受众标准」直接判定。符合标准不另要维护者批准；与标准不符是具体
  审查意见，不是待决定。
- **待决定**：只有真实边界扩大才需要维护者的明确决定：实际扩大权限、凭证或发布
  信任，未在清单中声明的网络访问，以及重命名或删除已发布插件。审查策略或安全
  门禁被削弱同样需要维护者决定。查看原始决定记录与维护者权限，不能只相信作者
  自述。已有有效决定不重复问；后续越出该范围时才重新判断对应部分。
- **平台授权**：审插件 PR 时，除插件自己申请的 OAuth scope，还要核对它用到或依赖的
  Cindy 本体（宿主）授权：依赖哪项、平台是否已批准、宿主是否已发布。本体授权有变化
  或未就绪先不合，并把需要申请的范围一起规划。详见「第三方平台授权」。这不是维护者
  的个案决定；其它符合现有标准的改动仍直接判定。
- **普通维护**：文案、静态资源、已有功能修复、依赖维护、可追溯 vendor 补丁与生成物、
  保持安全边界的打包脚本修复，可由自动 reviewer 审核通过。路径只用于定位核查，
  不单独构成人工审批理由。无法确认来源/内容时列具体缺口，不推断安全。
- **执行合并**：已有维护者授权的合并程序在当前 head 的必需检查、有效批准、运行证据
  和线程处置满足后可执行；本次若插件自己的第三方 OAuth scope 有变化，或它依赖的
  本体授权有变化或尚未就绪，还须说明里写明平台已批准，用到本体授权的还须宿主已发布。
  无需再逐 PR 请求“合”。
  reviewer 身份本身不授予 merge/close 权限；没有执行授权时只报告结论，不绕过
  GitHub ruleset 或用管理员模式制造绿灯。

置信度分数不是额外的仓库合并门禁，不强制 clean 5/5。自动 approve 仍遵守配置的
riskCeiling 与 GitHub 有效 review 要求。符合准入与受众标准的不因「缺少产品批准」
拦住。真实权限、凭证或发布信任扩大，未声明的网络访问，或重命名/删除已发布插件，
在没有维护者对具体范围的明确决定时不自动批准；这种路由本身不应使代码 review check
失败。插件自己的 scope 或它依赖的本体授权有变化，且说明未确认平台已批准（用到本体
授权时还须宿主已发布）时，单列「等平台批准」，先不自动批准；不标成代码 P1，也不
因此让代码 review check 失败。已写明就绪的不重复拦截。

### 第三方平台授权

审插件 PR 时，除插件自己申请的第三方 OAuth scope（如 `oauth.scopes`），还要核对
插件用到或依赖的 Cindy 本体（宿主）授权。Google 通讯录这类范围可以由插件自己申请，
也可以走宿主共用的 OAuth 应用。同类会被平台安全审核卡住的授权同样适用。

- PR 说明写清插件新增或变更了哪些 scope、为什么要、平台审核状态；若用到本体授权，
  再写明依赖哪一项、平台是否已批准、宿主是否已发布。本体授权有变化，或未批准、宿主
  尚未发布的，先不合；就绪后更新说明再合。审查只核对说明是否写清，不代替平台做
  授权决定。
- 需要申请的范围按插件自身和它依赖的本体授权一起规划（例如通讯录只读和修改一起
  考虑），避免分开反复触发平台安全审核。用不上的不要申请，最小权限仍然成立。未一次
  规划只作提醒，不是缺陷。
- 只有这一类会被平台卡住的授权变动需要等待。准入、受众以及其它符合现有标准的改动
  仍按既有规则直接判定，不因此改成样样人工批，也不列入「待维护者决定」。

### 复审与提交者反馈

复审对照最新 head，将意见分为已修复、有据不采纳、待处理；已修复或证伪的意见
明确撤回，依授权回复/Resolve。无新证据不重新提出同一问题，不要求为非阻断偏好改码。
真实未解决的风险不能靠 Resolve 掩盖；同族问题一次检查相关入口，不以固定 review
轮数代替判断。只补验证受本轮变更影响的场景。

一次列出最小待办，并区分等作者、等维护者、等平台批准。准入与受众按标准判定，不单列「等产品决定」。
CI 等待 fork 批准、仓库基线故障或测试资源缺口由维护者承担，不要求作者修改无关插件。旧基线故障须核实，
不能因此忽略 PR 引入的新失败。无变化不反复催同一决定。

## 设计契约

### 授权跟随执行者

当前 Agent 工具调用内的普通 HTTPS 与 workdir 文件操作，使用 Host 下发且严格在途的
`callId` 复用 Cindy 既有 Agent 授权；CLI 继续走已有 Node 工作进程，工具是否执行由
当前 `ghost_call` 的既有 Agent 授权决定。不得仅为了预登记具体命令、域名或路径新增
Slot 或 Manifest 字段。只有 Panel、订阅、scheduler、常驻进程等脱离当前 Agent 调用的
自主 Host 能力，才必须在 `ghost.json` 直接声明；自主 Node Runtime 仍须声明顶层
`node`、固定入口和最小子进程边界。Host 托管凭证也仍须按声明守门。

### tool description 即契约

`ghost.json` 里每个 tool 的 `description` 与顶层 `whenToUse` 是 Agent 读到的唯一
使用手册。以下情形需核对具体影响；会导致错误外发、费用、数据损坏或核心功能失效
的按实际严重程度阻断，普通不影响使用的措辞差异不升级 P1：

- 代码行为边界改变（做什么 / 不做什么 / 返回什么 / 有何副作用）而 description
  未同步更新；
- description 夸大能力（声称能探测/校验实际上没有探测的东西，例如声称探测某
  API 门禁但实际只请求了无关端点）；
- 漏报副作用：写操作、外发数据、不可逆动作没有写进 description；
- 返回值语义变更（如从「精确值」改为「下限估算」）未同步到 description。

### skill 文档与 settings 文案纳入契约

插件内 `skills/**/SKILL.md`、settings 页提示文案、`ghost.json` tool description
三者对同一能力的表述必须一致。PR 改了其中任何一处的行为语义（能查什么/查不到
什么/费用口径/限制条件），必须核对另外两处是否同步；发现矛盾时说明实际影响，按上文口径定级。

### 多语言资源语义一致

`locales/` 下任一语言的 description/文案发生**语义**修改（不只是措辞润色），
必须比对其余语言（zh-CN/en/ja/ko）是否同步；语义矛盾（如一种语言说「本地估算」
另一种说「真实账单」）说明实际影响后定级。仅措辞差异不报。注意：settings 页自渲染文案的
语言覆盖遵循 `docs/localization.md` 的英文回退契约——缺 ja/ko 翻译本身**不是**
缺陷，不要要求补齐协议允许回退的语言。

### 同源状态逻辑双写一致

`main.js` 与 `settings.js`（或 worker）若各自实现同一状态判定（连接状态、默认
账号、额度、过期），修改一处时必须检查另一处口径是否一致；不一致（如 main.js
判过期账号无效而 settings 页仍显示已连接）说明触发路径和用户影响后定级。

### 错误信息说人话

面向用户的报错必须可行动：401 要提示去插件详情页填 token，403 要说明权限缺口，
连接失败要区分「配置错」与「网络不通」。禁止裸抛 HTTP 状态码、英文堆栈或
`error: undefined` 这类无信息文案。`main.js`/worker 中新增的错误分支未遵守时指出。

### 边界校验的设计层收敛

发现同一校验/状态问题横跨多个入口时，一次检查共享判据与相关调用，给出完整的
受影响范围。优先修复共同根因，保留已承诺功能；不要为了关闭意见新增无关机制，
也不要把精确行为改成估算或删除覆盖来回避缺陷。真实的新问题继续处理。

## 版本与发布纪律

### 版本必须递增

本仓发布流水线按完整包上传。为避免 Server 对同版本不同 SHA 返回
`RELEASE_VERSION_CONFLICT`，插件目录下任何被打进 `.cindy` 的内容发生变化时都必须
bump version，包括 name/description/author/icon 等展示字段；新版本必须使用
`major.minor.patch` SemVer，且严格大于 `main` 上的当前版本。新插件只校验 SemVer 格式，
不做大小比较。不要尝试在本仓复刻 Server 的元数据特例；CI 对完整包执行统一版本门禁。

### Server 与客户端交付契约

CI 必须在本仓校验全部 `ghost.json`，不得 checkout Cindy 或私有 Server 仓库；同时对
最终 `.cindy` 包执行 Server 与 Desktop 约束的交集：压缩/解压大小、条目数、
manifest/icon/locale/Skill/Manual 单文件上限、安全路径、大小写路径冲突、客户端保留
文件、声明文件存在性、四语言结构和文本长度。尤其是插件与 locale 的 description
不得超过 300 字符。放宽或移除安全/交付门禁需维护者批准；保持约束的正确性修复
不因文件路径转人工，须以实际打包回归验证。

官方仓提交的是 Server public release：禁止 `oidc-token` secret；携带 Manual 的插件
必须声明 `minCindyVersion`。不要用 Greptile 对
manifest schema 的猜测替代 CI 的确定性校验结果。

`.tests/plugin-contract.test.mjs` 同时接受未改动的 legacy v2 与合法 v3；但新插件，
以及实际打包内容发生变化的现有插件，必须在同一 PR 迁移到 `schemaVersion: 3`、
按该插件实际依赖填写首个已发布版本（正式稳定版或 Beta 版） `minCindyVersion`、移除 `slots` 并保持直接能力声明等价；
仓库不设置统一 Cindy 版本下限。
只改仓库级文档、CI 或其它插件时，不得要求顺手迁移无关的 v2 清单。

### 运行验证与证据复用

按实际影响核对运行证据，对维护者与外部作者同一口径，不要求固定 checkbox 或重复
抄写 CI 已提供的包哈希。验证可以由作者或维护者完成；PR 正文或链接到的评论/记录
均可，必须明确实际测试版本/来源、Cindy 环境、场景、结果和未测项。

- 新插件、新宿主能力、认证、安装/升级、运行时或跨进程变化，需相应的真实 Cindy
  集成验证。功能/UI 修复需在当前代码对应运行环境复现并验证受影响路径。
- 正式稳定版、Beta 或可识别来源的开发构建证据均应如实记录，并核对实际依赖的
  Host API/manifest 兼容性。开发构建不能冒充已在发布客户端验收；只有开发环境具备
  的能力不能作为声称已发布客户端兼容的依据，缺少的兼容验证仍需补齐。
- 已有验收覆盖且后续修改不影响的路径可以沿用，给出原证据与从已测版本到当前
  完整差异的适用说明；不得只看最后一次 commit，不能将旧包已测改写成新包已测。
  纯说明/翻译/元数据、无行为影响的文件调整不要求重新跑全部核心场景。
- 打包脚本修复以真实打包、文件清单、路径/限额与安装相关差异为验证目标；如产物
  的运行内容未变，不机械要求每个插件重新实机安装。图片/UI 修改仍核对实际显示。
- 审查者根据证据判断是否覆盖当前风险；覆盖不足列具体场景，不反复索要泛化的
  “重新验收”。已明确接受且仍适用的验收结论无需再次确认。CI 不能代替真实运行。

`minCindyVersion` 是兼容声明与分发依据，不保证直接安装一定适配；能力缺失时需降级
或明确升级提示，不绕过运行时授权。验收环境须满足插件实际依赖；降低或删除该字段
需维护者确认扩大范围及旧版本兼容证据。未改动旧插件不为补字段批量迁移。

### 能力声明的前向兼容

不得因为当前客户端尚未实现某项声明而新增发布/安装硬阻塞。支持格式内的未知能力
字段、Cindy 类目/动作、订阅事件和 legacy slot 应保留；仓库不维护另一套客户端能力
白名单。已知字段类型、包安全、凭证隔离和实际会话授权仍须校验。声明可发布不代表
接口已实现或自动授权；作者兼容要求见 `docs/plugin-authoring.zh-CN.md`。

### 发布与审核链路

国内推包 Workflow 保持移除，海外支持 `main` push 与从 `main` 手动触发推包。
Workflow 只能通过受保护的 Plugin Platform endpoint 提交，不得绕过 Platform 直接
调用 Plugin Server。Platform 负责创建 pending release、通知 reviewer 并记录批准/拒绝；
只有批准的 release 才能被兼容客户端发现；拒绝不改变已有的已批准版本。

## 新插件准入

### 插件准入与受众标准

新插件、新内置供应商，以及 `provisioning.json` 的 audience 变更（含首次登记和
扩大分发），按下面三条直接判定。符合标准即接受，不另要维护者批准，也不标成
「待维护者决定」。不符合是具体审查意见：写明违反哪一条，以及应改成哪一档
audience 或不予接受。拿不准但仍然有用时，按自选接受，不要升级成个案审批。

`ghost.json` 的 `author` 必须是真实作者，不得冒充官方团队。

1. **`all`（装给所有人）** 须同时满足：多数用户受益；开箱即用，无需自备第三方
   密钥或账号；不绑定某一个人或某一个团队的流程；质量稳定。热度或投稿数量本身
   不能作为 `all` 的理由。
2. **自选接受**：有用但小众，或需要用户自己的密钥或账号。audience 写
   `{ "emails": [] }`，不自动安装，由用户在市场自行选择。
3. **不予接受**：非常个人（只服务作者自己的数据、流程或私有服务）；纯演示或示例
   （改放到 `docs/`）；或 Agent 不装插件就能直接完成的事。

只有真实边界扩大才需要维护者的明确决定：实际扩大权限、凭证或发布信任；未在清单
中声明的网络访问；重命名或删除已发布插件。维护者指本仓库的维护者集体。已有决定
覆盖的范围不重复索要；越出该范围才重新判断。准入与受众符合标准时，不把这类决定
当成前置条件。

### 打包时二进制依赖

`binary-dependencies.json` 是仓库构建输入，不是运行时权限。新增或改动依赖、
URL、SHA-256、文件映射、版本和许可证时核查实际变化；已有来源的维护更新不自动
转人工。新增不明来源、可执行下载或权限/信任边界扩大按上文审批。核查上游来源、固定字节、
六平台覆盖、完整再分发条款和最终包限额。通用资源或全平台归档可只声明一次下载，
不得要求作者机械填写六个 URL；平台覆盖声明不代替实际运行验证。哈希通过不代表内容安全。
公共打包器只能下载、校验、收集普通文件，并使用安装包自身的 ZIP 压缩；不额外编码依赖文件，
不开放作者构建钩子、不执行下载内容；
发布凭据所在 job 不得运行插件代码或依赖收集。沿用原有运行时权限判定，
不要把构建校验扩大成新的运行时硬阻塞。

### 功能查重（必查）

新插件或新内置供应商是否接纳、以及 audience，按「插件准入与受众标准」判定。提案
issue 或 Draft PR 可以记录设计，不是批准门禁；已有讨论可链接，不要求先经过维护者
确认再写代码。普通修复直接提 PR。reviewer 从仓库清单和相关 `ghost.json` 查找重叠
并提供证据，不把逐个通读全部清单或取得每位原作者同意的成本交给提交者：

- 功能场景明显重叠（如又一个通用网页搜索、又一个同一邮箱服务商的客户端、
  又一个 Mermaid 修复）：列出具体重叠点（哪个现有插件、哪些能力重合），并要求
  PR 描述中说明差异化定位与共存理由；
- whenToUse 的场景枚举与现有插件大面积重合、或 network.hosts 白名单高度重合且
  面向同一服务时，同样列出供人工判断；
- 合理共存不提示：同一服务商的不同产品（gmail/drive/calendar/sheets）、同一
  协议的不同服务商（163/icloud/qq/yahoo 邮箱）不算重复。

此项为 review 提示，不直接判 fail。重叠是否合理按上文共存口径判断并写明证据；
不要把查重改写成待维护者决定。符合准入标准时不另要维护者确认提案或 audience，
后续技术 review 可自动批准。不予接受时写明不符合标准的哪一条，或与哪个现有插件
构成重复的通用能力；使用当前事实，不引用已修复的缺陷。

### 新插件必备项

新插件 PR 缺以下任何一项时逐条指出：

- `ghost.json` 使用 `schemaVersion: 3`、按该插件实际依赖填写首个已发布版本（正式稳定版或 Beta 版） `minCindyVersion`、
  不含 `slots`，并以直接顶层字段声明能力；
- `provisioning.json` 有对应条目，且 audience 符合「插件准入与受众标准」（`all`
  或自选 `{ "emails": [] }`）；PR 描述写明落在哪一条；
- `ghost.json` 的 `author` 是真实作者，不冒充官方团队；
- 四语言 locale 资源齐全（zh-CN/en/ja/ko，`.tests/localization.test.mjs` 口径）；
- `ghost.json` 的 icon 引用有效、assets 体积合理；
- bundle 了第三方依赖的插件（如带 Node worker 的邮件类）必须随包提供
  `THIRD-PARTY-LICENSES.txt`（完整许可证文本）。注意：ignorePatterns 只是不逐行
  review 该文件的内容，**文件缺失本身必须报**；
- PR 描述包含实机验证说明（在 Cindy 客户端安装 `.cindy` 包实测过哪些工具）；
  没有实测的必须如实标注，reviewer 应在 summary 里显式提示「未经实机验证」。

现有 v2 插件不做专项批量迁移；但 PR 一旦改变该插件目录内会进入 `.cindy` 的实际
打包内容，就必须在同一 PR 把清单迁移到 v3，并保持能力等价。只改仓库级文档、CI 或
其它插件时，不得要求顺手迁移未触及的 v2 清单。

## 其他判定口径

### 图片资源

普通图标/截图核对格式、路径、体积与 manifest 引用，使用可用预览检查实际显示。
没有读到像素不得声称检查了内容；确有内容/版权疑问或缺少必要预览时列具体待办。
不因图片扩展名一律升为高危或点名要求维护者确认。SVG 活动内容、原生可执行文件和
无法追溯的预编译资源须检查对应执行风险，不能按静态 PNG 处理。

### summary 与置信度表述

只要存在经核实仍成立的未解决 P1（本轮或历史轮未修复且未被证据驳回），
summary 首行必须显式写「存在未处理的 P1：<列表>」；禁止在 P1 挂起时输出
「可安全合并」类措辞。置信度分数必须与证据一致，不能替代问题处置。summary 分开列代码阻断、
待验证、待决定和等平台批准；等平台批准只在插件自己的 scope 或它依赖的本体授权有
变化，且说明尚未确认平台已批准（用到本体授权时还须宿主已发布）时列出。
audience 与准入标准不符列入具体审查意见，不写入待决定。非阻断
建议不混入硬门禁。

### 已接受限制（勿再报）

`.tests/localization.test.mjs` 的 stripJsComments 不识别正则字面量：正则内的
`//` 会被误判为行注释开头。此为维护者确认的已接受限制（代码头注释已声明）：
该盲区只吞标识符 token、吞不掉探测行为本身——探测结果必须有消费者（赋值/比较/
传参），消费者在他行则标识符照拦，消费者在同行则整行为死代码、语义上等于无
探测；扫描方向 fail-closed（最坏是误报，不放行）。现有插件源码中该模式零出现，
不要针对此点重复报 P1。
