# 预约里程碑的介绍与配置沟通

用户询问玩法、术语或如何准备时,按本指引解释;实际查询、配置和审核操作见 [runbook](taptap-suite/references/taptap-reserve-milestone/references/reserve-milestone-runbook.md)。纯咨询不要求先提供游戏、内部编号或图片,不启动上传或提审。下面的句式仅用于说明沟通方式,不代表已经执行成功;人数、奖品和数量必须来自用户认可的方案或已核实配置。

## 先解释玩法与名词

用户问「预约里程碑是什么」或「有什么用」时,可以这样介绍:

> 在游戏预约期,你可以用预约里程碑向玩家展示开服奖励,吸引感兴趣的玩家提前预约。每一档对应一个预约人数目标和一份奖励,最多可配置三档,也可以先配一档。正式公测开服后,按实际达成的档位发放奖励。审核通过只说明方案获批,人数是否达标、奖励是否已发放都要分别确认。

按用户当前问题解释相关概念,不一次展示整张术语表:

| 名词 | 面向用户的解释 |
| --- | --- |
| 档位 | 一组「预约人数目标 + 奖励内容 + 奖励图片」,不是奖励库存或每人领取次数。 |
| 预约目标 | 这一档设定的目标人数,按 TapTap 预约口径;各档目标依次增加。目标值不是查询到的当前预约人数。 |
| 奖励原图/灰图 | 灰图和彩色原图是同一份奖励的两种展示。预约人数刚好达到目标时仍可能显示灰图,是否达标请看对应档位的预约进度。提供符合规格的彩色原图即可,上传时会生成灰图。 |

用户问「和签到有什么区别」时,说明里程碑按游戏预约人数设置奖励目标,签到按玩家累计签到天数配置奖励;不把签到的库存、兑换码或集卡设置搬进里程碑。

可以用「达到第一个预约目标对应第一档奖励,达到更高目标对应后续档位」解释阶梯结构。示意不等于当前游戏规则;不自行给出默认人数、奖品或领取方式,不承诺奖励自动到账或具体发放时间。询问当前是否达标、玩家如何领取或能否看到页面时,只依据实际核实的信息回答,配置查询不足以证明这些结果。不主动附官方文档或未经核实的活动链接。

## 从了解玩法到准备方案

- **首次配置**:先沿用已知游戏,询问准备配几档、各档目标人数、具体奖励及数量。不默认配满三档,不把「礼包」展开为未经认可的道具清单。奖励应为可兑现的游戏内奖励,不包含实物或金钱。
- **追加档位**:读取当前配置后,说明哪些档位保持不变、还可加几档,候选与当前配置完全一致时,告诉用户「这些档位已经生效,本次没有新增档位」。有新增时只补问新增项。例如:「前两档保持不变。第三档准备在多少预约时达成,奖励是什么?」
- **素材准备**:先核对已提供或可复用的图片,只列缺少的档位。需要新图片时说明「请提供该档奖励的透明背景彩色 PNG,200×200 像素、100 KB 以内;灰图会在上传时生成。」用户问某张图能否使用时,给出实测尺寸、文件大小和透明背景检查结果;指出不符合的具体规格。未核实的图片属性如实说明。不要求用户搬运图片地址,不用其他档位图片代填。
- **确认本次目标**:已明确只整理、只上传、提交审核或撤回时直接沿用。只有「配置一下」等表达确实无法确定范围时,说明没有单独后台草稿,再问是先整理方案还是提交审核。咨询不变成配置问卷,已给齐的信息不重复询问。

领取方式、库存、活动标题、开始结束时间不是本域配置字段,不照搬签到问卷作为提审必填项。用户另问兑现或领取规则时可以说明已确认的业务信息,但不能声称这些内容已写入本次配置。

## 给用户看的配置预览

写入前先展示本次内容与影响。内部请求预览不能替代用户可读的业务预览,写后汇报也不能补作写前预览。方案与影响已展示且授权覆盖时继续执行;用户一次给齐具体方案并授权时,说明本次动作即可,不再重复确认。只有新增或改变未确认内容时,集中确认差异。

预览先用游戏名称说明目标,再按实际内容列出:

| 档位 | 目标预约人数 | 奖励内容与数量 | 图片准备情况 | 本次变更 |
| --- | --- | --- | --- | --- |
| 按实际档位逐行展示 | 用户认可的目标值 | 用户认可的完整奖励文案 | 已有图片沿用/本次原图待上传/缺原图 | 保持不变/新增/修改未生效方案 |

该行是结构说明,不能原样作为用户方案。人数可用「万」展示,但须保持精确值;奖励数量不省略。仅一档时用短句即可,不为表格重复罗列。图片用所选文件或对应档位描述,省略存储地址。图片已上传不代表已绑定、生效或实际展示正常。

预览还要说清本次动作与缺项:

- **只整理方案**:列出完整方案和缺项,说明尚未提交审核;不要写「后台草稿已保存」。
- **仅上传图片**:说明为哪档准备图片,完成后停在素材准备,不顺带提审。
- **提交审核**:区分保留档位与本次变更;缺图或规则阻断未解决时先说明缺口,不把不完整方案展示成可提交。
- **替换待审方案**:说明需要先撤回原申请再提交新方案,展示两份方案的差异;授权未覆盖撤回或重提时,只确认尚未覆盖的部分。
- **单独撤回**:说明撤回哪份待审方案,不会撤下已有生效奖励,也不会自动提交另一份方案。

## 按证据汇报结果

下面的措辞仅在对应事实已经核实时使用;每次只报告本次范围、实际状态和仍待完成事项。

| 已核实的情况 | 对用户的回复方式 |
| --- | --- |
| 仅整理方案 | 「方案已整理,尚未提交审核。还缺第三档奖励图片。」无缺项时不虚构待办。 |
| 图片上传成功,尚未提审 | 说明已准备的原图与灰图。若只校验了本地文件和上传回执,可说「已取得原图和灰图地址,尚未验证远端图片能否打开,也未验证玩家端展示」。若已打开图片,仅将远端可访问列为已验证。 |
| 提交前检查通过 | 把三件事放在同一段,例如首次配置时说「这三档满足提交条件,目前尚未提审,也尚未生效」。追加时说清哪些档位已生效、哪些新档仍待提审。 |
| 提审后回读为审核中 | 首次配置且当前没有生效档位时,可说「预约奖励方案已提交,正在审核。目前还没有生效的奖励档位。」追加时说明哪些档位已生效、哪些新增档位仍在审核。按本次回读结果逐档列出目标预约人数和完整奖励文案(含数量),包括沿用的档位。 |
| 审核通过但未核实生效 | 「本次方案已审核通过,是否已生效仍待确认。」不说已上线、已达标或已发奖。 |
| 指定的申请查不到 | 「未找到这份审核申请。」再查询当前奖励配置,按这次查询结果答复。 |
| 配置已生效,用户关心展示 | 按平台报告实际核实的范围。例如:「两档配置已生效。Android 已开放预约,两档人数、奖励文案和图片都已核对。iOS 仍为敬请期待。」若只核对了文案,就明确「图片展示待核实」。 |
| 主动撤回且回读确认 | 「本次审核申请已撤回。」存在已核实的旧生效方案时补充「原有生效奖励保持不变」;不描述为平台驳回。 |
| 平台驳回 | 说明实际审核原因及需要调整的未生效部分,不编造原因或自动修改奖励。 |
| 写入结果无法确认 | 说明哪一步结果待核实,保留此前已经确认完成的内容,不说成功、失败或已自动重试。 |

厂商可以看到审核进度、生效情况和实际的审核意见。审核中且没有审核意见时,直接说「正在审核」,省略空的驳回原因。审核未通过时,用中文说明具体原因和需要调整的档位。
