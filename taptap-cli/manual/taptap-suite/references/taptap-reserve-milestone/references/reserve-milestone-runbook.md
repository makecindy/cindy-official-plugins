# 预约里程碑 runbook

本文是 Agent 的执行参考,不是默认用户回复模板。按 [预约里程碑手册](taptap-suite/references/taptap-reserve-milestone/MANUAL.md) 分流,仅阅读当前场景;用户明确要求技术用法时才展示调用细节。示例 ID、路径、人数和奖励不是业务默认值。

所有方法属于 `reserve-milestone`,使用已确认的 `developer_id` / `app_id`,其余输入放 `data`。返回字段从 CLI 的 `data.result` 读取;查询历史返回 `list/page/page_size/total`。能力未出现时核对 `list_tools(category:"reserve-milestone")` 与方法 schema,不改用其他域或原始接口。

玩法、名词解释、业务预览及结果措辞按 [用户指引](taptap-suite/references/taptap-reserve-milestone/references/reserve-milestone-guide.md);以下状态与字段用于内部执行,不直接展示给用户。

## 信息确认与分步提问

按 [共享提问规则](taptap-suite/references/shared-execution.md#交互提问方式) 收集当前阶段的缺项;已给齐就继续,不强制每个阶段都问一次。

| 当前情形 | 只补问什么 | 不替用户决定什么 |
| --- | --- | --- |
| 首次配置 | 每档目标预约人数、具体奖励及数量;图片是否已备好 | 不默认配满三档,不自行编奖励或人数 |
| 追加档位 | 新档目标、奖励、缺失原图 | 不重新询问或修改已生效档位,不为新档腾位删除旧档 |
| 调整未生效方案 | 本次变更项;存在待审记录时是否授权撤回并改为新方案 | 不把「改文案」默认扩展为撤回、重提 |
| 仅准备或「先保存」 | 只有意图不清时说明无后台草稿,并询问先整理方案还是提交审核 | 已明确只准备时不上传、不提审 |
| 查看进度或历史 | 多个记录确实无法消歧时才请用户选择 | 不启动配置问卷,不让用户查内部 ID |
| 只缺素材 | 在聊天中说明哪档需提供原图及规格 | 不用文字选择工具索要附件,不要求用户制作灰图 |

奖励面向正式公测开服,人数按 TapTap 预约口径。奖励描述应清晰、可兑现,不包含实物或金钱;不凭方案推断当前已达到预约目标或已经发奖。特殊平台素材需平台处理,不自行替换奖品使请求通过。

## 执行顺序与完成条件

| 阶段 | 动作与进入条件 | 本阶段完成证据 |
| --- | --- | --- |
| 现状 | 读取当前与提交记录,区分首次配置、追加、查询、撤回 | 已确认目标游戏、已生效档位与待审冲突 |
| 方案 | 保留已生效前缀,只整理授权变更 | 完整档位方案与缺口清单;仍未写入 |
| 素材 | 仅在本次授权包含上传且文件齐备时上传缺失原图 | 同一次响应的完整原图/灰图对;单独上传到此结束 |
| 候选检查 | 实际传入完整 rewards 调用只读检查 | `ready=true`;解释 warnings,阻断未解决不能提审 |
| 提审 | 方案未变、检查通过且已获提审授权 | 返回提交 id,并回读该记录的完整档位和审核状态 |
| 生效核实 | 用户要求核实结果时再次查询 | `current` 与目标方案一致且 `is_active=true`;仍不证明客户端展示或发奖 |

只准备方案且信息齐全时可以只读检查;缺图时保留缺口,不能编 URL 使检查通过,也不能为了检查而擅自上传。准备与图片上传都不产生可回读的服务端草稿。

## 场景 A:看现状与定位记录

```text
call_tool(name:"reserve-milestone get", args:{
  developer_id:"<developerId>", app_id:"<appId>"})
```

读取 `current` 与 `submit`:前者是当前生效记录,后者是指定的提交记录,未指定时取最近提交记录;未指定编号时,无对应记录的字段会省略,不造一条空记录或用另一侧填补。两者可能同时存在、内容不同。每条记录含 `id/status/raw_status/is_active/rewards/audit_reason/created_time/updated_time`,奖励项含 `slot/bonus_at/bonus_text/bonus_icon/bonus_grayscale_url`。

有已知提交记录时指定它,避免将另一条最新记录当成本次结果:

```text
call_tool(name:"reserve-milestone get", args:{
  developer_id:"<developerId>", app_id:"<appId>",
  data:{submit_id:"<submitId>"}})
```

显式指定的申请不存在或不属于该游戏时,整次查询返回 `404 not_found`。告诉厂商未找到这份申请。单独执行不带 `submit_id` 的 `get` 核实当前配置,不将最近提交当作原申请。

用户要查历史,或需要按提交时间和奖励档位定位申请时,按需读取历史。提审或撤回结果未知时,已有申请编号就先按编号回读,没有编号再查历史。

```text
call_tool(name:"reserve-milestone list-history", args:{
  developer_id:"<developerId>", app_id:"<appId>",
  data:{page_size:20}, page_all:true, page_limit:1000})
```

页码从 1 起,每页最多 100。按完整奖励集合、记录 ID 和时间核实目标,不只按文案匹配;有多个候选时用提交时间、档位与状态帮助用户选择。查询失败或覆盖不完整不等于无记录,不能据此重新提交。

### 审核状态与生效判断

只按 `status` 枚举名判断审核进度,`raw_status` 仅供排查,用 `current` 和 `is_active` 核实是否已生效。

| 内部判断依据 | 对用户的含义 | 可继续的动作 |
| --- | --- | --- |
| `current` 省略 | 目前还没有生效的奖励档位 | 查看 submit 后决定是否准备首次方案 |
| `MILESTONE_STATUS_UNDER_REVIEW`(`1`) | 奖励方案正在审核 | 查询;获撤回授权后可撤回,不重复提交 |
| `MILESTONE_STATUS_APPROVED`(`2`) | 审核通过 | 再核对 current/is_active,不能直接说已生效 |
| `MILESTONE_STATUS_REJECTED`(`3`) | 平台驳回时说「审核未通过」,确认是主动撤回时说「申请已撤回」 | 结合 audit_reason 和已执行动作说明;可整理新方案 |
| `current` 对应目标且 `is_active=true` | 该方案当前生效 | 保留其档位,可在上限内准备新增档位 |
| `MILESTONE_STATUS_UNKNOWN`(`0`)、`UNRECOGNIZED`(未识别的数值)或缺失状态 | 暂时无法确认这份申请的审核进度 | 保留事实并核实,不推断可撤回或可修改 |

撤回是主动动作,但记录仍使用驳回状态。只有已执行的撤回及回读原因支持时才说「主动撤回」,不能把任意驳回都解释成撤回。

## 场景 B:准备与调整方案

1. 从已确认的生效配置、用户方案或选中的未生效记录整理候选。不自动套用其他游戏、历史最新或示例奖励。
2. 候选与生效配置完全一致时,说明已生效且没有新增档位,停止提审。驳回或撤回的新增档位尚未生效,仍可调整后重新检查。首次配置允许连续 1–3 档;追加时逐项保留 `current.rewards` 的人数、文案、原图和灰图,再添加新档。输入数组位置就是档位,不提交只含新增档位的局部数组,也不将历史的 `slot` 直接写进输入。
3. 人数为正整数、严格递增、最多 99999999;奖励文案非空且最多 25 个 UTF-16 字符。图片必须有真实 HTTPS 原图/灰图对。已生效历史值超限或存在空档时不修剪、重排或猜测填补,说明当前不能按该方案提交,交平台核实。
4. 已有三档生效而用户想加第四档,或要求修改任一已生效字段时,说明限制后停止相应写入,不把新需求改成替换原奖品。
5. 有待审记录且方案完全一致时,报告已有申请审核中。需要更改待审方案,先整理本次变更和素材缺口,按场景 E 处理撤回授权;不能只因出现待审记录就撤回。

全量输入由 Agent 组织为会话工作目录内的 `milestone.json`,每项仅含 `bonus_at`、`bonus_text`、`bonus_icon`、`bonus_grayscale_url`。下例只说明结构,实际值来自用户与回读/上传结果;人数和文字不得当作默认方案:

```json
{"rewards":[{"bonus_at":10000,"bonus_text":"用户确认的游戏内奖励","bonus_icon":"https://example.com/reward.png","bonus_grayscale_url":"https://example.com/reward-gray.png"}]}
```

未修改的生效档位不重新上传图片,即使新图片看起来一样,URL 改变也属于修改该档。以前上传且已确认可复用的完整图片对可以沿用;来源不明、只有一张图或没有可靠灰图时先补素材。

## 场景 C:准备奖励图片

本域上传要求 **200×200、100 KB 以内、透明背景彩色 PNG**。向用户说明每张候选图是否可用,给出实测尺寸、文件大小和背景情况。按用户指定的「档位 → 文件」配图;用户要求沿用历史图时,按已确认的记录和档位复用原图、灰图。文件名中的 tier 序号只能作为线索。若同一奖励的历史配图与文件名指向不同,或多张图都可能对应同一档,先列出候选,集中问清缺少的对应关系。预览中逐档列出所选文件或历史来源,只上传本次用到且尚未取得图片对的文件。

```text
call_tool(name:"reserve-milestone upload-reward-image", args:{
  developer_id:"<developerId>", app_id:"<appId>",
  data:{image:"rewards/tier-1.png"},
  idempotency_key:"<imageIntentKey>", dry_run:true})
```

已有上传授权且预览正确时,同 key 把 `dry_run:true` 换成 `yes:true`。`image` 是本地文件路径,必须是相对会话工作目录的路径;它不是 `_positional`,也不要加 `@`。不要使用通用素材上传代替此流程,也不要求用户提供存储凭证。

成功返回 `bonus_icon`、`bonus_grayscale_url`、`width`、`height`、`size_bytes`。完整保存同一响应的两张图,只分配给已确认档位;没有 asset_id,不拼灰图 URL。上传成功只表示素材已准备,配置仍未提交。需要核实图片是否可用时,检查原图和灰图的可访问性、格式和尺寸;图片可用不代表已绑定到奖励档位。提审后还需按提交 ID 回读图片绑定。

部分失败或结果未知时保留原文件与 key,停止依赖该图片的提交;该域没有独立素材查询能力,不能假称已经回读验证,也不自动换 key 重传。说明哪一对图片尚未确认齐备,再按实际可恢复信息处理。

## 场景 D:检查与提审

候选包含完整档位和真实图片后,真实执行只读检查,不能用 dry-run 替代:

```text
call_tool(name:"reserve-milestone check-readiness", args:{
  developer_id:"<developerId>", app_id:"<appId>",
  data:"@milestone.json"})
```

结果 `ready/checked_scope/blockers/warnings` 表示当前快照的候选检查;`checked_scope` 为 `candidate_milestone_submission`。`ready=false` 时先解决返回的首个阻断,再检查余下问题;输入格式或必填错误也可能直接报错。缺少检查结果不当作通过;warnings 不表示平台审批已完成或 URL 文件真实性已验证。

向用户展示完整方案、保留与新增档位、奖励与图片,说明执行后直接进入审核,没有保存草稿阶段。只要求准备方案时到此结束;已有提审授权且内容未变时不重复索要确认。

```text
call_tool(name:"reserve-milestone submit-review", args:{
  developer_id:"<developerId>", app_id:"<appId>",
  data:"@milestone.json",
  idempotency_key:"<reviewIntentKey>", dry_run:true})
```

核对 scope 和完整请求后,同 key 把 `dry_run:true` 换成 `yes:true`。上传和提审使用各自意图的 key;不能用提审 key 重复执行不同配置。

同一调用者在同一厂商、游戏和操作下,用原 key 和相同请求内容,可以回放成功保存后 24 小时内的回执。回执是当时的快照,查当前状态用 `get`。幂等记录仍在时,同键换内容会冲突;记录过期后,再执行同一命令可能新建申请。

提审超时或结果未知时,停止写入。有申请编号就按编号回读,没有编号就查历史并逐档核对。短时未查到仍应报告结果待核实,不自动重提。下游可能稍后完成,此时换键重提可能创建重复申请。

受理结果为 `action=submitted`、`id` 和 `snapshot`。保存返回 id,用场景 A 的 `submit_id` 回读同一记录,核对所有人数、文案、图片与状态;不能只凭 action 判断审核中或生效。读到不同内容或无法回读时保留待核实,不自动再次提交。

准备度反映查询时的状态。同一游戏正在提审或已有待审申请时,新提审会被拒绝。用户问进度时回读并报告已有申请;需要调整待审方案时按场景 E 确认撤回和重提的授权。

## 场景 E:撤回与驳回恢复

若用户要求先确认,核对目标并说明撤回影响后结束本轮,等待用户明确同意撤回这份申请。等待期间仅可查询或预览。收到确认后,按同一 submit_id 重新核实仍在待审,再执行撤回。

单独撤回:已有 submit_id 和新鲜状态可复用,否则按场景 A 读取目标。只有该记录处于待审核状态且授权包含撤回时执行:

```text
call_tool(name:"reserve-milestone withdraw-review", args:{
  developer_id:"<developerId>", app_id:"<appId>",
  data:{submit_id:"<submitId>"},
  idempotency_key:"<withdrawIntentKey>", dry_run:true})
```

同 key 执行 `yes:true` 后,结果 action 为 `withdrawn_as_rejected`;按同一 submit_id 回读驳回状态及「用户主动撤销审核」原因,同时保留并核对原生效方案。该操作不是撤下已生效奖励,也不生成独立 withdrawn 状态。

调整待审方案时,先备齐完整新方案。缺图时保留原申请,取得上传授权后先上传并核实原图和灰图。展示完整方案及差异,确认所有可提前检查的条件均已满足,再按授权撤回并回读。重新读取生效配置,核对候选仍适用后,按场景 D 检查、提审;撤回授权不等于重提授权,已有覆盖两步的授权不重复询问。

平台驳回时解释实际 `audit_reason`,只改用户同意修改的未生效部分,保留生效前缀,再检查和按授权重新提交。不要自动替换奖励、修改已生效档位或宣称已撤下原奖励。

## 场景 F:审核通过后

1. **定位过审申请。** 已知申请编号时,用场景 A 的 `get` 按 `submit_id` 回读。只有游戏和奖励线索时,先查当前配置和历史,按审核状态、奖励和提交时间定位。历史可能有多条过审记录,无法唯一确定时请用户选择。
2. **核对当前生效档位。** 确认 `submit.id` 是目标编号、`submit.status` 为 `MILESTONE_STATUS_APPROVED`。仅当 `current.id` 也是该编号且 `current.is_active=true`,才将这条申请报告为当前生效。逐档对照档位序号、目标人数、完整奖励文案、原图和灰图,有已确认的提审方案时一并核对。回复中列出每档人数和奖励。若当前生效的是另一份方案,分别说明本次申请的审核进度和当前生效的奖励,用提交时间或档位内容区分。若缺记录或档位有差异,说明仍待核实的内容。
3. **确认目标平台已开放预约。** 按用户要核对的平台查看同一游戏的线上发布状态,或在玩家详情页切到该平台,确认显示「预约」或「已预约」。Android 和 iOS 分别核实。游戏资料已上线、草稿已选「预约」都不能证明该平台已开放预约。若仍为「敬请期待」,说明哪些档位已生效、哪个平台尚未开放预约,到此结束展示核对。仅看到「关注」且无法读取线上状态时,说明预约状态待核实。核对展示无需修改发布状态或替玩家预约。
4. **逐档核对玩家详情页。** 在同一环境、同一游戏、已开放预约的平台查看「预约奖励」。按档位用 `current.rewards` 对照页面上的目标人数和完整奖励文案(含数量),确认该档图片实际加载,并与该档的原图或灰图匹配。页面显示灰图时按 `bonus_grayscale_url` 核对,显示彩色图时按 `bonus_icon` 核对。人数刚好达到目标时也可能显示灰图;用户问是否达标时单独核对预约进度。页面返回 404、未出现奖励区域、缺档或图片未加载时,分别说明已核实的配置、平台和具体未验证项。仅凭后台预览或图片地址可访问,不能确认玩家页展示。
5. **发奖指引。** 用户问如何兑现奖励时,说明目标按 TapTap 预约人数计算,正式公测开服后按实际达成档位安排发放。官方建议通过游戏内邮件或站内信向全服玩家发放。选择礼包码时,可将多档奖励合成一组码,在开发者中心的礼包码管理中上传并提审;若限定预约玩家领码,需提前通过工单联系 TapTap 工作人员。过审核对到此结束,不代发邮件、上传礼包码或发奖。

## 阻塞与恢复

| 情形 | 停在哪里 | 下一步 |
| --- | --- | --- |
| 待审记录与目标一致 | 不新提审 | 报告已有申请状态 |
| 待审记录与新方案不同 | 不擅自撤回 | 说明差异与影响,补齐撤回/重提授权中尚未覆盖的部分 |
| 生效档位不可改、已满三档或历史超限 | 停止该配置写入 | 保留现状,说明需平台处理;不重建绕过 |
| 图片不合规格或缺灰图 | 不提交不完整候选 | 补正确原图或核实已有完整图片对 |
| 只读检查失败 | 不提审 | 解释实际阻断并修正后复查 |
| 提交/撤回结果未知 | 停止写入,不自动重试 | 有 id 按该记录回读;无 id 查历史核对完整方案,无法唯一确认就保留待核实 |
| 无权限或能力缺失 | 停在当前步骤 | 按共享规范核实,并说明实际阻塞 |
