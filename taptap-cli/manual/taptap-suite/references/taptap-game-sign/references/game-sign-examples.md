# 面向厂商的签到介绍、案例与配置沟通

用户问“集卡是什么”“和普通签到有什么区别”“有没有例子”，或首次配置时表示不了解集卡，先解释玩法并提供以下两个案例，再按需询问是否开启。纯咨询不进入创建流程，也不要求先提供游戏、活动 ID 或素材；已有明确选择不重复询问方案，兑换条件与消耗按下文说明。

## 用户问“集卡是什么”时

先直接回答，再提供案例并说明可选的卡片组合。下面是可面向用户的介绍，按问题长短调整，不附内部执行说明：

> 普通签到按累计签到天数领取对应档位的奖励；开启集卡后，还可以收集卡片、兑换额外奖品。
>
> 玩家集齐 3 种基础卡各 1 张，再加上对应的奖品卡 1 张，就能兑换这张奖品卡对应的奖品。每次兑换会消耗这套卡片，想再兑换一次，就需要重新集齐。
>
> 你可以看看这两个活动，了解加不加集卡有什么区别：

**带集卡的签到活动**
https://www.taptap.cn/events/game-sign/jpry1tf8

**普通签到活动**
https://www.taptap.cn/events/game-sign/xcmcw801

## 四种或五种卡片怎么配

面向用户说明：

> 可以配 4 种卡片：3 种基础卡和 1 种奖品卡。三种基础卡分别设置名称和图片；奖品卡除了名称和图片，还需要配置对应奖品、奖品图片、抽中概率、库存及兑奖说明。奖品卡可以选择保留紫色或金色的一种。
>
> 也可以配 5 种卡片：3 种基础卡和 2 种奖品卡，两种奖品卡分别对应各自的奖品、概率和库存。
>
> 兑换时，需要集齐 3 种基础卡各 1 张和对应的奖品卡 1 张，每次兑换都会消耗这套卡片。两种奖品卡不需要同时集齐；兑换另一项奖品时，也要重新凑齐一套基础卡。

已有卡片名称时用实际名称逐张说明，三种基础卡分别列出名称、图片和缺项，不合并成一个含糊的“基础卡”条目。四卡方案只列所选的一种奖品卡；不要把未保留的另一种奖品卡列为待配置，也不要套用其他活动的卡名和素材。只有进入配置且方案未定时，再问“这次准备放一种集卡奖品，还是两种？”。

### 案例使用边界（仅供 Agent 执行）

两个活动链接用于展示带集卡与普通签到的区别，不代表目前仍可参加。只有用户询问能否参与、页面不可用或容易误解时，才补充活动是否仍可参与。未读取页面时不声称看过页面具体内容。

案例奖品、概率、库存、文案和素材不能自动套用到当前游戏。卡片获取条件和抽卡次数以该活动已确认规则为准，不编造每日抽卡次数或保中奖。介绍只用“基础卡”“奖品卡”等业务用语，编号、枚举和概率换算留在内部。

首次配置集卡的回复中，即使用户已选四卡或五卡，也要简短说明上方的兑换条件与消耗：三种基础卡各 1 张加对应奖品卡 1 张，兑换消耗整套卡，五卡不要求两种奖品卡同时集齐。当前会话已说明且用户理解时不重复。上述兑换机制直接说明，不反问用户决定是否消耗或是否同时集齐；具体规则文案仍须来自用户确认的方案或已验证配置，不自行编写未经用户认可的活动规则。

## 从了解玩法到确认配置

以下是面向厂商的沟通顺序，不是每轮必发的问卷。只展开当前问题；用户已给出的选择和信息直接沿用。所有实际名称、数量、状态来自用户或已核实配置，下面的句式不代表已经执行成功。

| 当前需要 | 给厂商看的说明与下一步 | 内部处理 |
| --- | --- | --- |
| 了解玩法 | 简短解释玩法，提供两个活动案例，说明四种或五种卡片的组合。纯咨询到这里即可。 | 不创建活动，不要求身份或配置素材。 |
| 选择是否集卡 | 用户准备配置且尚未决定时问：“这次只做签到领奖，还是也加上集卡玩法？”说明增加集卡还需准备卡片图片、额外奖品及库存。 | 沿用已有活动方案；只询问缺项。 |
| 确定集卡方案 | 问：“这次准备放一种集卡奖品，还是两种？”解释每种奖品对应一张奖品卡，并同时说明上方的兑换条件和消耗规则。 | 分别映射为 3+1／3+2；只有需要区分已有目标卡时才展示卡名、颜色或图片供选择。 |
| 准备内容 | 先汇总已收到的素材，再说明还缺哪些卡片名称与封面、奖品内容与奖品图、抽中对应奖品卡的概率、库存、兑奖期限和领取说明；按实物／兑换码分支收集。 | 字段、格式转换和保存顺序按配置文档处理，不把接口字段表交给厂商填写。 |
| 确认方案 | 按下面的预览结构展示将配置的内容、未齐事项及本次动作。删卡按 [删除预览](taptap-suite/references/taptap-game-sign/references/card-collection.md) 展示。 | 内部定位 ID 并生成请求预览；所需规则未明确就补问，不代填后再要求用户兜底确认。 |
| 汇报结果 | 说明实际保存了什么、还有什么待完成、是否已提交审核。例如仅在已核实时说“集卡配置已保存，奖品库存仍待补充，尚未提交审核。” | 保存、库存核实、自检、提审分别判断；不把接口成功直接说成活动已上线。 |

卡片封面与奖品图分别确认用途。用户只提供奖品图时，不擅自把它用作卡片封面；用户已明确同意共用同一图片时沿用该授权，并检查图片是否符合对应用途的规格，不重复确认。缺少封面时列为待办，按下方部分保存规则处理，不先代填再让用户更换。

## 给厂商看的配置预览

保存或删除前，必须向厂商展示本次具体方案及影响，并核对已有授权。内部 dry-run 不等于厂商已看到预览；写后汇报不能补作写前预览。同一方案及影响已展示并获确认时直接执行，不再确认；用户一次给齐具体方案并授权时沿用授权，写前说明本次动作即可。只有新增或改变了未确认的内容／影响，才集中询问该差异并等待回答，不把每张卡拆成一轮确认。

用户未提供或认可的规则、领取说明不能作为完整配置保存。可以基于已确认业务事实起草建议文案，但必须先展示并确认新增文案；没有证据的游戏内入口或领取步骤先补问，不编造。已有明确文案或已核实且无需修改的现有规则直接沿用，不要求用户重新确认，更不能先保存再说“有自己的文案可替换”。用户仅要求部分草稿时按其范围保存并说明缺项。

先说明活动名称、签到时间与兑奖截止时间、是否包含集卡；每日签到奖励和集卡奖品分开列。已给定名称就使用名称，不拿示例活动或其他厂商的奖品填充预览。

开启集卡时，按以下内容展示；信息少时用短句，不为表格重复罗列：

- **集卡方案**：3 种基础卡 + 1 种或 2 种奖品卡。先写完整含义，需要时再附“3+1／3+2”简称；这里说的是卡片种类，不是奖品库存或每人抽卡次数。
- **基础卡**：卡片名称、可用图片与尚缺素材。不列奖品、库存或概率的空占位列。
- **奖品卡**：卡片名称、对应奖品、可用图片、抽中该卡的概率、实际库存与待办。概率按百分比展示，库存按实物件数或可用兑换码数量展示；未知就说明待核实，不写成 0。需要准备的数量与实际已入库数量分开说。
- **兑奖与领取**：集齐 3 种基础卡各 1 张和对应奖品卡 1 张，才能兑换该项奖品；兑换会消耗这套卡。另列已确认的领取方式、期限及实际规则，不承诺抽到奖品卡就直接获得奖品。
- **本次动作与缺项**：说明准备保存、修改、补库存或提审中的哪一步；只列当前缺少的信息，不把后续计划表述成已完成。部分保存时，写入前说明本次保存哪些、哪些因缺项暂不保存及原因，例如“这次先保存三张基础卡；两张奖品卡还缺封面，暂不保存”。仅在已有授权涵盖本次部分保存时执行，这句是动作说明，不新增一轮确认；未获授权或与用户要求不符时，仍按上方规则只确认差异。写后按实际保存范围汇报，不能说整套配置已完成。

介绍、提问、预览、进度和异常说明都遵循同一输出口径：对厂商讲业务事实、影响和下一步，不讲接口实现、端之间的差异或排查过程。内部编号、枚举、字段名、概率换算、服务端预置槽位及幂等键留在执行层；不要在中文说明后括号补出原值。用户明确要求技术用法时才提供对应细节。例外也不允许编造活动规则或将示例配置当成用户已确认的方案。

## 发送前检查

逐项检查回复正文、表格、括号和活动名称后的补充：不复述任何内部编号（包括审核、活动、奖励、集卡和卡片 ID），不展示原始枚举或 JSON 字段名。厂商用编号定位、用 SR／SSR 指卡时，内部据此定位，对外仍使用活动名、卡名和中文类型。日期、数量、概率、素材尺寸等业务数字照常展示，不做数字一刀切删除。仅当用户明确要求接口调试、命令或具体编号时，按需提供必要原值；提到编号本身不等于要求回显。

厂商问编号是否会出现在玩家页面时，不能从助手隐藏编号的规则推断页面行为。没有实际页面或前端依据时说明“目前还未核实玩家页面是否展示这个编号”，按需核对具体页面后回答，不声称“按设计不会展示”。

未实际核对展示效果时，不声称图片“能正常显示”或“不会裁切”；保存成功仅说明配置已保存。图片规格不符合要求时明确说明具体差异，不把规格要求改说成可忽略的建议。

结果汇报遵循 [回读与结果说明](taptap-suite/references/taptap-game-sign/references/card-collection.md)，让厂商知道哪些已经核对、哪些仍待核实。
