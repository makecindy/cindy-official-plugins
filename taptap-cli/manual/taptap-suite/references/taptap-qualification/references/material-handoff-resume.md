# 全类型资料交接与接续

## 先查能力和事实

APK、Windows、H5、Tap 小游戏、Spark 共用 `get-qualification-assessment` 判断要求。包体类型、分发平台和关卡身份是三个独立维度，不互相推断。APK + Windows 逐域核对；未知或冲突保留未知，不默认 false、不改类型。

先读取目标环境的命令说明（schema），确认下列操作是否可用。CLI 不支持的材料由用户在开发者后台办理。完成后，使用 CLI 查询保存情况、审核进度和生效状态，确认后继续后续流程。自动化调用仅使用 CLI 支持的接口，不直接请求网页内部接口，也不能用应用资质写接口替代小游戏专用接口。操作能力以目标环境返回的 schema 为准。

## 根据返回事实决定下一步

接口给出状态、能力限制与阻塞原因，不替用户选择办理页面。CLI 与手册结合当前 schema、用户意图和敏感信息约定决定下一步；不能把一次拒绝操作直接解释为“必须去后台”，也不能从通用上游错误猜出具体缺少哪些材料。

| 返回事实 | CLI 与手册的操作与接续 |
| --- | --- |
| `contacts_required` | 说明联系人未保存；按敏感信息约定请用户本人在开发者后台填写，不索取正文。保存后查询隐私进度，确认存在标记及剩余阻塞，再决定是否提审 |
| `PRIVACY_SUBMISSION_BLOCKED` | 查询隐私进度，逐项解释 `submit_blockers`；已有在审/生效材料不重复提交，需要补正文时由用户本人填写，保存后重新查询 |
| `INDEPENDENT_PRIVACY_WITHDRAWAL_UNAVAILABLE` | 查询审核状态；`version_review` 按下方整版撤回流程办理，不能代撤未知或不在审核的记录 |
| `ICP_RECORD_UPDATE_UNSUPPORTED` | 当前 H5 保存/提审入口不支持该记录，不代表 ICP 被驳回。查询独立进度；已通过不重复办理，需更新自身 ICP 时按实际能力和敏感信息约定交给用户本人办理，完成后查进度与 assessment |
| `QUALIFICATION_DOMAIN_UNSUPPORTED` / `QUALIFICATION_DOMAIN_UNKNOWN` | 先核对目标版本和实际包体，再查询对应材料命令的能力；隐私、备案优先使用支持的独立命令。通用资质入口不支持不代表 CLI 不支持，只有具体能力不足或涉及本人填写的敏感资料时才交接开发者后台 |
| 资质或适龄审核不支持单独撤回 | 先区分资质审核单与资料版本审核。只有确认属于可撤回的资料版本且用户明确确认整版影响后，才转 app-edit 手册的 `withdraw-app-review`；独立资质审核单不能套用资料版本撤回。当前 CLI 不支持对应整单撤回时，请用户在开发者后台确认处理，完成后查询资质审核状态；不把单项撤回自动扩大为整单撤回 |
| `H5_FILING_SCOPE_UNSUPPORTED` | 核对当前环境、归属、关卡身份和实际类目；先纠正选错的目标。确认该入口不支持但用户仍需办理时，再核实其他命令能力或交接开发者后台，不切换身份或场景绕过限制 |
| `FILING_STATE_NOT_EDITABLE` | 查询当前备案状态；在审等待、通过后不重复提审，不能将不可编辑解释为缺少材料 |
| `FILING_OWNERSHIP_MISMATCH` / `FILING_VERSION_MISMATCH` / `PRIVACY_SCAN_VERSION_MISMATCH` | 核对当前厂商、游戏、绑定和所选版本；有歧义先向用户确认，不自动改目标或发起写操作 |
| `MATERIAL_SNAPSHOT_MISMATCH` | 重新读取对应资料快照，展示变化并确认本次操作意图，再按当前条件准备操作，不重放旧快照 |
| `PRIVACY_DECLARATION_UNCONFIRMED`，或查询/上游调用失败 | 保留“尚未确认”，不当作正文缺失、不要求重新填写。只读核查状态和请求编号；写请求结果不确定时保留原幂等键，不盲目重试 |

用户完成交接后，由 CLI 重新查询保存、审核和生效状态，确认达到对应条件后再接续；用户口头确认不能代替读回结果。

## 每次开发者后台交接都交代清楚

告诉用户要在哪个环境、哪个厂商和游戏的哪一版资料中，填写或核对哪项材料，为什么需要本人办理，以及完成后 CLI 如何确认结果。交接记录仅保留上述信息、已确认的页面入口和查询命令。不要保存联系人、证件正文、签名下载链接、验证码或拒审原文。链接必须来自当前环境已确认入口，不猜测网站地址或具体页面链接。

原因分别说明：

- 用户选择：材料敏感，用户不愿交给 AI；即使有写接口也尊重选择。
- CLI 不支持：当前命令不支持该文件格式、材料类型或操作。
- 人工动作：主体认证、签约、短信/人脸核验、平台审核。
- 状态限制：资料冻结、随版本审核、不支持单独撤回等。

“已在网页填好”只触发重新查询，不直接认定已提交或通过。CLI 查询时分别确认是否已保存、是否在审核、是否已生效；修改申请被拒时，仍需单独核对已生效材料的状态。查询失败不能解释为未填写，不能自动补写。

## 小游戏隐私接续

适用于服务端允许维护隐私的国内 H5、Spark、Tap 小游戏。APK/Windows 普通隐私仍按 assessment 的实际域处理，不能转用此流程。

1. 读取 `qualification get-mini-app-privacy-progress` 的 schema 并查询目标游戏；使用返回的独立隐私 `snapshot`，不是 assessment 的快照。
2. `review_state` 描述当前申请；`effective_state` 描述线上声明。`contacts_saved` / `retention_saved` 与项目数量仅证明存在，不证明每项内容正确。无声明、资料缺失或用户需修改正文时，用户在开发者后台填写，CLI 不索取联系人、不读取完整正文、不要求复制回来。
3. 用户保存后重新查询。普通联系人保留在服务端；提交时复用完整原稿，不传空联系人、不清空已保存材料。已在审核中不重复提交；返回 `version_review` 时，说明隐私材料随资料版本一起审核；需要撤回时，转 app-edit 手册核对待撤回的资料版本及其关联隐私记录，说明整版撤回的影响，取得用户确认后使用 `app withdraw-app-review`；随后查询版本和隐私审核状态。命令不可用或无法确认对应版本时，再请用户到开发者后台核实办理。不能用独立隐私撤回命令代替整版撤回，也不能将资料版本撤回用于整份资质审核单。
4. 需要独立提审且用户已授权时，先从包体查询确定真实 `version_id`，读取 `qualification prepare-mini-app-privacy` 的 schema，以 `{"version_id":<实际版本>}` 准备报告。准备是写操作，使用幂等键；不等于保存或提审。
5. 准备结果只有 `state_analyzed` 且有 `report_key` 时继续。`state_partial` 表示扫描未形成完整可用结果，`state_unavailable` 表示当前没有可用结果；都不能提交，也不证明隐私声明填写错误。先查询所选版本的包体归属和上传解析状态；包体未就绪先完成包体流程。包体已就绪但仍无报告时，向用户说明扫描服务尚未提供可用报告，请维护者核查该游戏、版本和请求记录；不要反复准备、重传包体或改隐私声明碰运气。接口未返回具体原因时明确“原因尚未确认”，不猜成网络故障或缺少联系人。扫描有局限不能推断不处理个人信息；报告过期或与包体不一致时，确认目标包体后再按需准备。实际提交还会由业务服务校验完整已保存声明与报告是否一致。
6. 再读隐私进度，核对 `submit_blockers`，读取 `qualification submit-mini-app-privacy` 的 schema。预览的输入只有 `expected_snapshot`、`version_id`、`report_key`；以稳定幂等键提交。这个命令不会新建正文，也不提交资料版本。
7. 提交后重新查询隐私进度和 assessment，核对审核记录及状态。审核通过再重新进行资料预检，不把提审成功当作生效。
8. 撤回须有明确意图，读取 `qualification withdraw-mini-app-privacy` 的 schema，传独立隐私快照。仅无 `withdraw_blockers` 的独立审核可撤回；操作后查询审核退出及存在标记，不声称已核对隐藏正文内容。

### 对照汇总与独立隐私进度

先确认环境、厂商、游戏相同，再区分应用资质审核单、独立隐私审核单和资料版本审核。先后查询之间可能发生审核变化；遇到不一致只读重查，不能拿不同审核对象的阻塞项互相替代。

- assessment 的 `has_saved_material=true` 只说明已确认存在材料，不代表填写完整或已生效；`pending_upload` 也不能单独解释为“从未保存”。独立隐私的当前申请看 `review_state`，线上生效情况看 `effective_state`。
- assessment 的 `submit_blockers` / `withdraw_blockers` 针对通用应用资质入口；`qualification_domain_unsupported` 表示该入口不能办理此材料，不表示独立隐私未在审核。小游戏隐私的具体操作条件以独立隐私进度和对应命令为准。
- 独立隐私 `submit_blockers=[]` 仅表示已保存声明没有已知状态或内容阻塞，查询时尚未校验所选包体的扫描报告。仍需按上方步骤确认 `version_id` 和有效 `report_key`，不能跳过准备或提交时校验。
- `no_processing=true` 时不能仅凭 `contacts_saved=false` 或 `retention_saved=false` 要求补联系人和保存期限；按该声明实际阻塞项判断，不擅自改变用户声明。

向用户解释原因与下一步，不只展示英文代码：

| 原因码 | 说明与接续 |
| --- | --- |
| `saved_editable_draft_required` | 当前没有可提审的已保存草稿；先查当前申请，审核中等待，已生效不重复提交，确需修改时由用户保存正文后再查 |
| `declaration_items_required` | 当前声明缺少处理项目；请用户本人核对实际处理内容并保存，CLI 再查询，不从扫描结果替用户填写 |
| `contacts_required` / `retention_required` | 当前声明缺少联系人或保存期限；请用户本人补充对应内容，保存后再查阻塞项 |
| `independent_review_required` | 当前不是可单独撤回的隐私审核；草稿、已结束审核无需撤回，随版本审核按上方整版核对流程办理；未知状态先查清 |
| `qualification_domain_unsupported` | 当前通用资质入口不支持此材料域；查询对应专用命令及进度，不直接要求用户重新填材料 |

首次“不处理个人信息”声明按 app-edit 手册的受限准备/提审流程办理，须用户真实确认；不能为了补齐隐私改选不处理。复杂声明先由用户保存，不从扫描结果推导出声明答案。

提交前会检查材料是否发生变化，但不能阻止其他人在检查后继续编辑。材料变化重新查询确认；请求超时先读回，保留原幂等键，不盲目新建审核。

## 备案、ICP 和主体

读取 `qualification get-mini-app-filing-progress` 的 schema。查询按当前游戏归属返回实际记录及 scene、资料审核、备案、ICP 各状态，不回传主体、证件、附件、核验数据或拒审自由文本。

- `record_exists=false`：未查到当前记录，不代表豁免；回 assessment 判断是否需要。
- H5 备案与游戏自身 ICP 分开说明：`review_state` 表示备案总审核状态，`filing_state` 与 `icp_state` 分别表示备案和自身 ICP 进度。H5 备案完成不能说成自身 ICP 已通过。
- 自身 ICP 的 `icp_status_approved_icp` / `icp_status_processed_icp_result` 表示通过；`icp_status_pending` 表示准备资料，`icp_status_submitted_icp` / `icp_status_sms_verification` / `icp_status_under_review` 表示办理中，`icp_status_rejected` 表示驳回。向用户说明具体阶段，不把办理中当成已完成。
- `icp_status_not_required` 是 H5 自身 ICP 未启用的初始状态，不能据此断言不存在 ICP 记录、已经通过或永远不需要办理；有既存记录时请用户在开发者后台核对，不直接要求重新上传。`icp_status_unspecified` 或无法识别的值表示独立进度尚未确认，不能用 H5 总状态代替。
- 同时查询资质清单与独立备案进度：资质汇总保留 H5 前置备案在审/驳回的约束，因此自身 ICP 已通过时，整体仍可能未完成；独立状态缺失时，汇总可能依据服务端确认的已有 ICP 记录判定。两者不要求状态文字相同，应说明各自依据。汇总为 `pending_upload` 只表示尚未确认完成，不证明没有材料，不自动重新提审。若汇总与明确的独立状态矛盾，保留待办并核对服务端结果，不选择较乐观的一项继续。
- `requires_sms_verification=true`：本人在开发者后台或正式核验渠道完成，不要求验证码交给 AI。完成后重新查询，不能仅凭用户回复判定通过。
- `self_icp_pre_approval_ready` 只描述自身 ICP 的前置资料：为 true 不代表主体信息和核验全部完成，为 false 不能直接认定是 H5 游戏备案提审失败的原因。确需办理自身 ICP 时，请用户在开发者后台核对适用的版署回函或版号材料，完成后 CLI 重新查询；不能据此额外阻止 H5 游戏备案提审。
- 无法确认记录属于当前游戏、服务查询失败或返回无法识别的状态时，说明暂时无法核实并保留待办；不当作没有记录重新创建。

### 非关卡 H5_GAME 保存与提交

H5_GAME 保存与提审仅支持服务端认可的非关卡 H5/UrhoX 类目；Spark 必须按实际类目和准入条件判断，不能仅凭 Spark 名称宣称可办。关卡及其他备案场景由用户在开发者后台办理。已有记录的自身 ICP 已开启或状态尚未确认时，也由用户在开发者后台继续办理，不用 H5 简介保存/提审接口替代自身 ICP 表单。

先查询备案进度和真实包体列表，确认用户选定的 `version_id`。读取 `qualification save-h5-game-filing` 的 schema，输入备案查询返回的 `expected_snapshot` 与版本；简介只有用户要求修改且已确认内容时才传，省略保留。著作权人由服务端按认证主体资料生成，不要求用户通过此命令填写或修改。主体与证件由服务端复用已保存材料，不传个人证件，不要求填写整个通用备案表。

备案记录的 `version_id` 与当前绑定的主包体版本可能不同，不自动选最新或主包体覆盖备案。继续已有备案时，先向用户说明备案版本与主包体的区别，核对备案版本仍属于该游戏并确认办理目标；确需换版本时，仅在记录可编辑且用户明确选择后保存。待审补提必须保留原版本和原简介。隐私扫描版本也不能直接当作备案版本。

遇到 `FILING_VERSION_UNAVAILABLE` 或 `FILING_VERSION_MISMATCH`，重新查询当前游戏包体列表并请用户确认实际版本；版本仍在但关联包体不可用时请维护者核查，不改游戏归属或随意换版本。仅有通用 404/400 时，先核对命令 schema、游戏作用域和所选版本；不能直接判为接口未部署。

保存成功后重新查询，确认记录、场景、版本，再用此次查询返回的快照按 `qualification submit-h5-game-filing` 的 schema 提审。先 dry-run、明确确认、使用幂等键；之后读回状态。主体资料不齐时，说明缺少的材料并请用户在开发者后台补充，完成后 CLI 再查询备案进度并核对提交条件；包体不支持或不满足办理条件时，说明服务端返回的原因，不能承诺补填即可解决。不伪造资料、不换场景、不改类型。

提审只返回通用 422 时，先只读查询备案进度和所选包体，说明已确认的状态及仍未知的拒绝原因。`ICP_RECORD_UPDATE_UNSUPPORTED` 表示此接口不能安全更新现有 ICP 资料，请用户在开发者后台继续办理，回来后重新查询确认；其他明确原因按其含义处理。若没有明确原因，保留请求标识、游戏和版本供维护者核查，不把某个同时为 false 的字段当作根因，不自动补材料、换包或重复提交。

普通 ICP/通用前置备案、主体认证、签署与外部核验仍由用户直接办理；完成后 CLI 查询备案进度和资质清单，列出已完成、审核中及尚未确认的事项，再按实际提交条件继续。不得将备案保存回执当作资质已生效。
