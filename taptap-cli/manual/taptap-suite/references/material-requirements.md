# 游戏物料要求

本文件维护 TapTap CLI 对游戏图片、视频和 Windows 专属素材的取证与回答口径。完整的官方 v4 规则目录见 [TapTap 上架规则目录](taptap-suite/references/official-review-rules-v4.md)，业务 skill 不应各自复制或补造一套规则。

## 规范来源

1. [游戏物料要求](https://developer.taptap.cn/docs/store/release/publish/material/)用于格式、尺寸、容量、时长、比例和物料用途。
2. [TapTap 游戏审核规范细则](https://developer.taptap.cn/docs/store/release/publish/agree/)用于物料内容、商店配置、安装包和资质审核规则。
3. 两份页面在 2026-08-20 显示版本 `v4`；引用时必须保留文档名和章节，完整映射见 [TapTap 上架规则目录](taptap-suite/references/official-review-rules-v4.md)。
4. 具体游戏的精确字段规格，以 `get-app-module` 当次返回的 `image_spec` / `video_spec` 为准。
5. 官方指南与实时规格不一致时，不混用两套数值；说明官方指南是通用参考，并按实时规格判断当前游戏能否上传或提交。

## 事实来源分层

每条结论必须标记一种来源类型，不能混写；本表是来源类型字段与边界的唯一正本：

| 来源类型 | 可以说明什么 | 不可以说明什么 |
| --- | --- | --- |
| `official_rule` | 两份 v4 文档明确写出的规则 | 文档没有出现的审核口径或检测阈值 |
| `current_fact` | 当前字段、包体、版本、资质和预检返回 | 永久规则、未来状态或未返回的数据 |
| `historical_review` | 指定版本的审核原文和发生时间 | 当前问题仍存在、官方文档一定有对应条款 |
| `test_evidence` | 指定包体、设备或素材的测试结果 | 未覆盖环境也通过、测试等于审核通过 |
| `agent_assessment` | 图片、视频、文案的语义风险判断 | 服务端已确认、官方规则原文或确定性通过 |

两份文档没有写“宣传片与实机录屏内容不得高度雷同”，也没有指定具体设备测试矩阵。此类内容只能按历史审核或测试证据展示。

## 回答规则

- 没有 `appId`：只说明通常需要游戏图标、横版宣传图、1:1 宣传图、游戏截图、宣传片 / 实机录屏；PC 游戏还需要 Windows 专属封面与 Logo。提供官方指南，不给固定尺寸表。
- 已有 `appId`：读取 `basic-info`、`assets-upload`、`profile-promotion`；PC 场景再读 `windows-exclusive`。逐项返回当前字段值、动态规格和不满足项。
- 用户只询问规格：只读取和判断，不调用 `save-changes`。
- 机器可判断的格式、大小、时长、分辨率和比例应直接指出；核心玩法、配音、字幕、画中画和设备 UI 等内容要求作为人工检查项说明。
- 每条官方内容提示附文档名称和章节；不能定位章节的判断不得标为官方要求。
- 最新版本有 `review_rejected` 时，相关审核原文单列为“历史审核风险”，并说明当前字段或包体是否已变化、是否仍无法验证。
- 上传或写入前重新读取目标字段规格，不能用旧会话、固定文档或其他游戏的规格代替。

## 主动提示时机与统一文案

以下三个时机都要主动提醒用户，而不是等用户追问：

1. 创建游戏成功拿到 `appId` 后。
2. 资料或素材写入完成并完成写后读回后。
3. 用户明确提出提交审核后、进入正式提审链路前。

可使用以下用户-facing 文案，并把 `<缺失项>` 替换为本次读取结果中确实缺失或不符合的项目：

```text
请按规范完善游戏图标、简介、开发者的话、游戏截图、宣传图、实机视频及当前可见且适用的首页推荐素材选项。
当前仍需处理：<缺失项>。
系统默认图标仅用于完成游戏创建，不代表已通过素材审核；如未替换为符合要求的正式图标，可能导致素材审核不通过并影响首页或编辑推荐展示。是否阻断提审，以当前字段 required、服务端预检结果或适用的官方物料要求为准。
游戏资料或版本审核通过，不等于素材审核通过，也不等于已经具备首页推荐资格。
```

这段提示的边界：

- “游戏图标、简介、开发者的话、游戏截图、宣传图、实机视频”是主动检查清单，不代表每个场景都无条件必填；实机视频和 1:1 宣传图等适用条件按当前字段与官方章节判断。系统默认图标只解决创建阶段的占位，不可据此判断素材审核已通过。
- 本次读取结果确实缺少图片素材时，提示缺失项后必须询问用户是否有可用的本地素材或真实游戏截图；用户确认没有本地素材后，再询问是否需要为图标、宣传图或 Windows 素材生成本地候选图，并转 `taptap-asset-library`。游戏截图只能来自真实游戏画面，不得使用模型生成虚构截图。视频缺失时只询问用户是否有本地视频，不提供图片生图流程。
- 缺失或内容不符合官方要求时，可以说明“存在素材审核不通过风险”；只有当前 `required=true`、服务端返回 blocker，或适用官方物料要求明确为必填时，才能说明会阻断本次提审。
- 游戏资料/版本审核、素材审核和首页推荐是不同判断；前者通过不能替代后两者的结果，素材审核未通过或推荐素材缺失时可能影响首页或编辑推荐展示。
- 首页编辑推荐栏目推荐图没有提供时，官方物料要求只支持“不展示在该专属栏目”的结论；不能把所有素材缺失统一改写成“只能通过搜索、分享链接访问”或“确定无法上首页推荐”。访问路径和具体推荐结果仍须以当前状态证据为准。
- 是否能通过搜索、分享、商店页或推荐入口访问，分别以当前版本状态和 `platform-status` 返回的可见 `region_flag_*` 为准；没有当前状态证据时标记为无法确认。

## 实时规格是否展示给用户

`image_spec` / `video_spec` 是当前游戏资料字段的可用性和校验约束，不是凭证或内部环境信息。CLI 可以向用户展示这些字段，用于解释素材为什么可用或不可用。

- 展示时应同时说明字段名与规格；不得把一次读取结果描述成永久规则。
- 规格只对本次读取的游戏和字段具有权威性。切换游戏、字段或资料状态后必须重新读取。
- 不展示请求 Cookie、Token、内部服务地址或调试上下文。
- 当实时规格与官方通用指南不一致时，以实时规格完成当前游戏的判断，同时保留官方指南链接作为通用参考。

## 合成数据示例

以下示例使用合成字段与规格，仅用于说明 CLI 可以向用户披露的结构。
它们不是任何真实游戏的读取快照，也不能用作其他游戏的固定常量。

游戏图标：

```json
{
  "field_id": "icon",
  "image_spec": {
    "aspectRatio": "1:1",
    "formats": ["JPG", "PNG"],
    "minHeight": 512,
    "minWidth": 512,
    "contentNote": "不要预加圆角"
  }
}
```

横版宣传图：

```json
{
  "field_id": "banner_4",
  "image_spec": {
    "aspectRatio": "16:9",
    "formats": ["JPG", "PNG"],
    "maxSizeMB": 4,
    "minHeight": 1080,
    "minWidth": 1920
  }
}
```

## 写入边界

- 图片按字段意图使用 `append`、`remove`、`replace` 或 `replaceOne`，并携带最新 `expected`。
- 视频先通过 `upload-video` 获得数字 `videoId`，转码可用后再写入字段。
- CLI 写入后重新读取字段，说明已完成项、剩余缺口和不满足的实时规格。
