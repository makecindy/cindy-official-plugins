### 1. 收集最小字段

必须先拿到：

1. 厂商角色（developer / author / publisher）：确认当前账号与该厂商的关系，不能从上下文默认或沿用历史对话。
2. 游戏名称：必须由用户明确确认。用户的一句话同时可能是名称、题材或版本描述时，先澄清它是不是最终名称；不能从 `test.apk`、`demo.zip` 这类通用文件名猜。
3. 游戏类型：必须有玩法上下文并映射到后台枚举；仅有名称时先追问玩法，有上下文后给 2-3 个推荐及判断依据，让用户选。
4. 包体类型：必须由用户在 APK / 小游戏 / PC / H5 之间确认，或由实际上传包识别；不能从名称、游戏类型或“极速版”等表述推断。

缺任一项时，不创建，只继续追问或给候选。

每个字段都要保留上下文来源：用户直接给出、用户从候选中选择，或工具从实际包体识别。只有模型推测、没有用户确认或工具证据的值，一律视为缺失。

### 1.1 选择题优先

用户只给了大方向、风格或玩法灵感时，优先使用当前宿主提供的可选择控件降低输入负担：

- 宿主适配：Claude Code 使用 `AskUserQuestion`；Codex 仅在宿主已提供 `request_user_input` 时使用；其他宿主使用等价选择控件。不要调用宿主未提供的工具。
- 控件优先：每轮只提交一个问题和当前组件支持的互斥选项；只有宿主没有选择控件时，才用编号文本提供相同选项。
- 逐步引导：一次只生成或确认一条创建必填信息，顺序为「厂商角色 → 游戏名称 → 游戏类型 → 包体类型 → 创建确认」。不要在同一轮同时展示多个字段和最终确认。用户选中当前项后立即记录，下一轮再问下一项。
- 歧义优先：例如用户说“帮我创建游戏，是电瓶车送外卖极速版本”，第一轮只给以下选择，不附带游戏类型、包体方向或创建摘要：
  - **正式游戏名**：将“电瓶车送外卖极速版本”作为最终游戏名。
  - **玩法 / 版本描述**：下一轮根据这段描述提供 2-3 个游戏名候选。
  不能直接推导为「名称=电瓶车送外卖极速版本、类型=休闲、包体=H5」。
- 名称候选：给 2-3 个可直接写入「游戏名称」的最终名称，不要只给命名风格。
- 游戏类型候选：给 2-3 个后台枚举可映射的中文类型，并说明一句判断依据。
- 包体类型：只在名称和游戏类型明确之后再确认；四选一且不得漏项 APK / 小游戏 / PC / H5，用一句话解释如何区分：APK=安卓手机安装包；小游戏=Tap 运行的小游戏包；PC=Windows 客户端包；H5=浏览器运行的网页包。
- 禁止组合候选：不要给「名称 + 游戏类型 + 包体类型」组合选项；资料文案不走选择题。

- 用户选定后记录当前答案并停止本轮；下一轮只追问下一个缺失字段，不要一次性铺开所有创建规则。
- 简介 / 首页推荐语 / 开发者的话等描述文案留到创建成功后交接 `taptap-app-edit` 处理，创建阶段不写。
- 名称、游戏类型、厂商角色以及可选的包体类型确认后，先用带稳定 `--idempotency-key` 的 `app create-app --dry-run` 预览；用户已经明确确认创建时，首个真实创建命令复用相同 `--data` 和同一个 key，并追加 `--yes`，不要先触发一次确认失败。

### 2. 包体类型判断

包体只能辅助判断包体类型和后续路径，不能代替游戏名称或游戏类型。

| 上传包体 | 创建方向 | 后续说明 |
| --- | --- | --- |
| APK 包 | APK | 适用于 Android 游戏；创建后继续上传或关联包体，并完善资料和合规认证 |
| 小游戏包 | 小游戏 | Tap 小游戏包需包含 `game.json`；创建后用 `upload-mini-app-package` 上传；分包测试不在 CLI 进行，上传后回 CLI 查询状态或关联已有包体 |
| PC / Windows 包 | PC | 适用于 Windows 游戏；创建后继续关联包体并完善 Windows 专属信息（转 `taptap-app-edit`） |
| H5 包 | H5 | H5 包需包含 `index.html`；主要在个人主页曝光，创建后继续上传包体并完善资料 |

APK / 小游戏 / PC 要求：

- 认证开发者才可发布上线。
- 需完整填写全部游戏资料。
- 必须完成所有游戏合规认证。
- 支持 APK、小游戏包和 PC 包。

H5 路径说明：

- 仅支持 H5 包体。
- 游戏仅能在个人主页曝光。

适用于所有创建方向的分发提醒：

- 创建后的「游戏类型与分发」状态以工具实际返回为准；创建阶段不能根据游戏类型或包体方向预设具体入口和状态。
- 分发状态的读取、解释与调整由 `taptap-app-edit` 的 platform-status 流程执行；创建流程内不自行调用模块读取或 `save-changes`。

### 3. 游戏类型推荐

游戏类型是枚举值。面向用户使用中文标签，工具入参可以用枚举 value。

| 类型 | value | 适合 |
| --- | --- | --- |
| 角色扮演 | `rpg` | 角色养成、剧情冒险、RPG |
| 休闲 | `casual` | 轻量、碎片化、放置、简单操作 |
| 动作 | `action` | 战斗、格斗、强操作 |
| 策略 | `strategy` | 策略、塔防、战棋、资源规划 |
| 模拟 | `simulation` | 经营、养成、建造、身份模拟 |
| 益智 | `trivia` | 脑力、知识、答题 |
| 街机 | `arcade` | 街机玩法、短局循环 |
| 冒险 | `adventure` | 探索、解谜冒险、剧情推进 |
| 卡牌 | `card` | 卡牌收集、构筑、对战 |
| 体育 | `sports` | 运动竞技 |
| 竞速 | `racing` | 赛车、竞速 |
| 解谜 | `puzzle` | 谜题、机关、推理 |
| 教育 | `educational` | 学习、儿童教育、知识训练 |
| 音乐 | `music` | 音游、节奏 |
| 文字 | `word` | 文字剧情、互动小说、多结局 |
| 桌游 | `board` | 棋类、桌面规则、派对桌游 |

推荐规则：

- 用户描述了题材和玩法时，给最匹配的 1 个主推荐，再给 1-2 个备选。
- 用户只给名称时，不要强行猜类型；请用户补一句玩法。
- 用户明确选择中文标签时，按该标签映射，不要改成更“聪明”的类型。

### 4. 包体方向指导

| 包体方向 | 适合 | 关键提醒 |
| --- | --- | --- |
| APK | Android 游戏，后续需要完整资料、包体和合规资质 | 认证开发者才可发布上线 |
| 小游戏 | Tap 小游戏包，后续需要完整资料和包体审核 | 创建请求会按 Tap 小游戏供给类型处理 |
| PC | Windows 游戏 | 后续还要补 Windows 素材和包体 |
| H5 | 浏览器运行的网页游戏、关卡或创意内容 | 主要在个人主页曝光，创建后继续上传 H5 包并完善资料 |

选择建议：

- 用户明确要使用 APK、PC 或 Tap 小游戏包，或需要完整商店页、后续提审：推荐对应包体方向。
- 用户明确内容在浏览器运行，并且只需在个人主页曝光：推荐 H5。
- 用户不确定时，说明四种包体方向的运行环境和后续差异，让用户选择，或让用户先上传包体自动识别；不得默认写入 APK。
- 用户说“发布后不要敬请期待 / 要提供游玩 / 要开放下载”时，把它记录为创建后的分发目标；不要在尚未读取实际可见的 `region_flag_*` 与各自 options 时猜入口、字段值或排除某种包体方向。

### 5. 创建后推进方式

推进方式是创建成功后的问题，不再作为创建前必填项。创建前只收集游戏名称、游戏类型、包体类型和轻量素材说明；创建成功后由 CLI 固定提供三个推进方式（开预约 / 测试 / 正式上线）供用户选择，这些后续任务不得反向影响创建判断。

| 推进方式 | 含义 | 创建后的引导路径 |
| --- | --- | --- |
| 开预约 | 游戏尚未准备上线，希望先展示游戏页并收集玩家预约反馈 | 创建后先由 `taptap-app-edit` 完善当前可见的基础信息和素材，再继续配置预约内容；开预约不要求传包或完成资质 |
| 测试 | 游戏希望先开放测试，验证内容和玩家反馈 | 创建后由 `taptap-materials` 盘点并逐项上传物料和对应包体，再由 `taptap-app-edit` 完善资料与合规项，最后交接测试计划流程 |
| 正式上线 | 游戏准备走提交审核和上线流程；这是目标方向，不是提交审核确认 | 创建后由 `taptap-materials` 盘点并逐项上传物料和对应包体，再由 `taptap-app-edit` 连续分析并补齐资料、合规项和分发状态；只有用户随后明确说“提交审核 / 提审”才进入提审流程 |

选项展示规则：

- 服务端不再返回 `intent_options`，CLI 在创建成功后固定提供上表三个推进方式：开预约 / 测试 / 正式上线。
- 三个推进方式是固定的，不依赖服务端返回，也不根据包体类型生成替代列表；标题和描述保持上表口径，不做业务改写或重新排序。
- 无论选择哪种推进方式，正式发布前都要单独确认工具返回且可见的 `region_flag_*` 分发状态；不要把“发布版本”和“调整分发状态”合并成一个隐含动作。
- “正式上线”选项只记录后续目标；未再次取得用户明确的“提交审核 / 提审”确认前，不得调用 `precheck-app-review`、`prepare-review-snapshot` 或 `submit-app-review`。
- 推进方式只影响创建后的任务清单，不改变创建游戏最小条件：游戏名称、游戏类型、包体类型。

### 6. 素材与说明

「素材与说明」用于收集创建前的轻量补充信息和首批物料，帮助助手判断意图、识别包体类型、生成资料草稿和创建后的发布准备清单。

首次回答口径：

- 用户首次询问“怎么创建 / 上架新游戏 / 需要准备什么”时，即使本轮只确认一个创建字段，也要主动说明后续通常会需要游戏 ICON、横版宣传图、1:1 宣传图、游戏截图、宣传片 / 实机录屏；PC 游戏还需要 Windows 专属封面与 Logo。不要等用户二次追问才提到素材。
- 规范来源、无 `appId` 时的说明边界和创建后的动态检查统一按[游戏物料要求](taptap-suite/references/material-requirements.md)执行。

可以利用的信息包括，但应保持轻量：

- 文字说明：一句玩法、版本状态、上线时间、发行计划、已有资质说明等。
- 图片：少量图标、宣传图、截图、横版封面等候选素材。
- 视频：少量宣传片、实机录屏等候选素材。
- 包体：单个 APK、小游戏包、PC / Windows 包、H5 包等，用于识别包体类型。

后续处理规则：

- 创建游戏前，素材与说明只用于分析和预填建议，不代表资料、素材或包体已经正式落库。
- 游戏图片是可选项。用户未提供 icon 时不阻塞创建，系统会使用默认图标；创建预览阶段不展示这一信息。创建成功后再说明系统默认图标仅用于完成游戏创建，不代表已通过素材审核；如未替换为符合要求的正式图标，可能导致素材审核不通过并影响首页或编辑推荐展示。是否阻断提审，以当前字段 `required`、服务端预检结果或适用的官方物料要求为准。不要输出“当前无 icon”这种内部字段式文案。
- 当前还没有 appId 时，不能直接判断物料是否满足资料审核条件；若开发者问「物料是否符合条件 / 下一步怎么做」，第一步应引导先完成创建游戏。
- 只有开发者明确说明游戏已创建，或已经拿到 appId 时，才按创建后物料检查路径说明；仍不得伪造或猜测页面链接。
- 创建游戏后的物料盘点与上传统一转 `taptap-materials`，按其盘点和逐项上传流程执行；文案文件由 Agent 直接读取，字段回填交 `taptap-app-edit`。
- APK、Windows、H5、Tap 小游戏 上传统一走 `taptap-materials`；上传成功不代表已绑定，资料页绑定由 `taptap-app-edit` 按包体槽位契约确认式执行。
- CLI 写入后重新读取资料草稿和包体槽位，说明哪些信息已回写、哪些仍需用户补充，并给出下一条 CLI 命令。
- `TOOL_NOT_IN_SCOPE` 必须停止当前流程，不得据此推断网页入口；页面入口规范按 shared execution「人工页面交接」执行。

### 7. 创建计划确认

创建流程最后一步为「创建计划确认」。创建前必须给用户确认摘要：

- 游戏名称，以及它来自用户明确名称还是已确认的名称候选
- 游戏类型（中文标签），以及对应的玩法依据和用户确认结果
- 包体类型，以及用户选择或包体识别依据
- 不单独展示发布模式；不得显示 `quick` / `regular`、“快速发布 / 常规发布”、“创建方式”或“发布形态”
- 创建预览只做业务抽象，不展示底层请求细节（方法、地址、参数、请求体）或原始命令
- 包体类型存在展示差异时，只说明与当前创建结果直接相关的影响，例如 H5 主要在个人主页曝光；不要在创建摘要中罗列不可用的后续能力
- 创建后仍需按工具实际返回且可见的 `region_flag_*` 确认分发目标
- 创建目标
- 后续流程
- 判断依据
- 创建预览不展示 icon 是否缺失、系统默认图标或补图建议；截图、简介等其他资料缺口同样留到创建成功后的 `taptap-app-edit` handoff

创建前判断和候选整理由当前 Agent 与剩余确定性读取能力共同完成：

- 有旧入口参数或用户目标不清时，忽略入口 ID 的历史语义，按“游戏名称 → 游戏类型 → 包体方向”逐项向用户确认，不猜发布意图。
- 有上传包体时可用 `app check-package-metadata` 辅助判断包体方向；有图片时先用宿主视觉判断用途，再用 `app check-image-spec` 推荐字段并查看规格提示。模糊或低置信度候选必须让用户确认。
- 对补充说明或文案文件，只生成 `title`、`description`、`developer_message`、`promotion_text`、`category`、`age_grade`、`developer_type` 候选，并说明来源和置信度。创建所需的名称、类型和包体方向仍要逐项确认；一句话推荐语最终由 `taptap-app-edit` 写入「首页推荐语」。
- Agent 直接对照当前创建目标、包体、图片和文案清单报告材料缺口；候选不代表已经创建游戏。只有用户确认的创建字段可以写入请求，创建后的资料字段补全统一转入 `taptap-app-edit`。
- 当前 metadata 已禁用 `get-compliance-status`；真实资质检查在创建后转 `taptap-qualification`。

**确认式创建流程**：

1. 先进入创建规划，不直接创建：整理已知信息、缺失字段、推荐游戏类型、包体类型判断、创建后任务清单。
2. 一句话存在“名称还是描述”的歧义时，第一轮只用选择控件确认名称语义；用户选择后，下一轮再基于玩法上下文提供游戏类型候选；类型确认后，下一轮才提供包体类型选项。每轮只推进一项。
3. 只有 `title`、`category`、`developer_role` 以及用户选择后才携带的 `package_type` 均有明确上下文来源时，才调用带稳定 `--idempotency-key` 的 `app create-app --dry-run` 检查最终请求。
4. 创建确认摘要必须说明：分发状态在创建后由 `taptap-app-edit` 按 platform-status 读取并与用户确认。
5. 创建确认摘要不显示 `publishMode`、`quick`、`regular`、“快速发布 / 常规发布”、“创建方式”或“发布形态”；只在包体选项旁说明具体影响。
6. icon 未提供时不在创建预览中展示；创建成功后再说明系统默认图标仅用于完成游戏创建，不代表已通过素材审核，并建议替换为符合要求的正式图标。截图、简介等其他资料缺口也在创建成功后交接。
7. 用户明确确认后，第二次命令复用完全相同的 `--data`，追加稳定的 `--idempotency-key` 和 `--yes`；标准流程只能是“预览一次 → 确认后创建一次”，不得省略 `--yes` 后再进行第三次重试。
8. 命中同名游戏时停止，不重复创建。
9. 创建成功拿到 appId 后，进入创建后 handoff：先交接创建信息和首批物料，再转 `taptap-app-edit` 先 `analyze-app-status` 总体体检（blockers / warnings / suggestions），并读取实际可见的 `region_flag_*` 状态，然后按当前包体能力过滤并展示推进方式；不要把回答停在“去编辑资料”链接。
10. `create-app` 返回 `TOOL_NOT_IN_SCOPE` 时立即停止。只说明当前 CLI 服务执行范围未开放创建能力并保留已确认的创建摘要；不要继续尝试直接工具、Raw API、网页或浏览器自动化。

### 8. 创建后下一步

创建成功后必须告诉用户下一步，而不是只说“创建成功”：

创建后推进计划必须参考 `taptap-app-edit` 现有 handoff 逻辑。

创建后 handoff 顺序：

- 创建成功后不能只输出「编辑资料 · 提交审核」链接。
- 也不能立刻跳到“检查资料缺口 / 上传包体 / 检查资质”的最终清单。
- 创建时未提供 icon 的，在这里说明系统默认图标仅用于完成游戏创建，不代表已通过素材审核，并建议替换为符合要求的正式图标；创建预览阶段不要提前说明。
- 同轮按[游戏物料要求](taptap-suite/references/material-requirements.md)主动汇总实际可见素材字段、动态规格和缺失项。
- 同轮主动提示：“请按规范完善游戏图标、简介、开发者的话、游戏截图、宣传图、实机视频及当前可见且适用的首页推荐素材选项。系统默认图标仅用于完成游戏创建，不代表已通过素材审核；如未替换为符合要求的正式图标，可能导致素材审核不通过并影响首页或编辑推荐展示。是否阻断提审，以当前字段 `required`、服务端预检结果或适用的官方物料要求为准。”
- 如果本次缺失项包含图片素材，紧接着询问用户是否有可用的本地素材或真实游戏截图；用户确认没有本地素材后，再询问是否需要为图标、宣传图或 Windows 素材生成本地候选图，并转 `taptap-asset-library`。不得为缺失的游戏截图生成虚构画面，必须要求用户提供真实游戏截图。
- 分发状态读取由 `taptap-app-edit` 的 platform-status 流程执行；创建流程内不自行调用模块读取命令。
- 完成分发状态读回后，仍只展示创建接口真实返回的推进选项；若接口未返回选项，不根据分发状态或包体类型补造候选。
- 用户选定后，再按该推进方式给出后续队列，并继续路由到资料编辑、包体上传命令、包体管理与自测或测试计划。
- 给用户的“下一步 / 准备清单”只做业务抽象，描述动作与目标，不贴原始命令或接口地址。
- 链接只能作为辅助入口附在末尾；给用户可点击链接时必须使用 CLI 当前 server 返回或推导出的完整页面 URL，不得写死开发、测试或生产域名。不要把链接当作唯一下一步，也不要用“去页面继续补”结束。
- 如果用户已有本地图片、视频或包体目录 / zip，创建成功拿到 appId 后转 `taptap-materials`，先执行 `materials +inspect`，再按 manifest 逐项上传。文案文件由 Agent 直接读取并交给 `taptap-app-edit`，也不负责创建 app。

创建成功后的推荐输出形态：

```text
已创建游戏草稿：<游戏名>
厂商：<developerId>
appId：<appId>
类型：<类型>
包体方向：<APK / PC / H5 / 小游戏>
若创建时未提供 icon：系统默认图标仅用于完成游戏创建，不代表已通过素材审核；请替换为符合要求的正式图标。
```

### H5 创建的返回边界

以下示例区分“本地 dry-run”和“真实创建成功”；占位符不能作为真实请求参数。不得把已有游戏的 appId 填入模拟回包冒充创建结果；推进方式由 CLI 固定提供，不依赖服务端返回的 `intent_question` / `intent_options`。`--dry-run` 返回的请求详情是内部执行信息，不回显给用户，面向用户只做业务抽象。

```text
call_tool(name:"app create-app", args:{developer_id:"<developerId>", data:{title:"<gameTitle>", category:"<category>", developer_role:"<developer|author|publisher>", package_type:"h5"}, idempotency_key:"<create-key>", dry_run:true})
```

```json
{
  "data": {
    "operationId": "createApp",
    "request": {
      "method": "POST",
      "path": "/app/v1/create-app",
      "query": {"developer_id": "<developerId>"},
      "body": {
        "title": "<gameTitle>",
        "category": "<category>",
        "developer_role": "<developer|author|publisher>",
        "package_type": "h5"
      }
    }
  }
}
```

用户明确确认后，使用同一份输入执行：

```text
call_tool(name:"app create-app", args:{developer_id:"<developerId>", data:"@create-app.json", idempotency_key:"<stable-key>", yes:true})
```

只有创建接口真实返回 `created: true` 后，才可把本次返回的 `app_id` 视为新游戏标识：

```json
{
  "data": {
    "result": {
      "created": true,
      "app_id": "<newAppId>"
    }
  }
}
```

创建成功只证明拿到新 appId，不代表包体、资料或提审已经完成。随后必须读取该新游戏的实际包体槽位和资料状态；不能拿其他已有游戏或历史执行记录代替本次读回。

推进方式由 CLI 固定提供（开预约 / 测试 / 正式上线），不再依赖服务端返回的 `intent_question` / `intent_options`。

H5 包体、完整物料包或目录的上传统一转 `taptap-materials`。Tap 小游戏 zip 同样走 `upload-mini-app-package`，上传产出 `miniAppArtifactId` 但不创建包体记录；分包测试不在 CLI 进行。
