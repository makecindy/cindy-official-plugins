# Review Risk Checklist

本流程把资料填写提示和提审前复核统一为可溯源的风险清单。规则来源只使用：

- [`official-review-rules-v4.md`](taptap-suite/references/official-review-rules-v4.md)
- 当前 CLI 读取结果
- 当前游戏的历史审核记录
- 明确提供的测试证据

## 来源类型

每条结论必须标记一种来源类型，不能混写。来源类型字段（`official_rule` / `current_fact` / `historical_review` / `test_evidence` / `agent_assessment`）与各自可说明的边界，以[游戏物料要求](taptap-suite/references/material-requirements.md)「事实来源分层」为唯一正本，本文件不另立表格。

## 填写资料时

用户查看、填写或替换资料字段时：

1. 读取目标模块的实时字段、`image_spec` / `video_spec`、当前值和可见性。
2. 从官方 v4 规则目录选取与目标字段直接相关的规则；只展示相关规则，不倾倒整份目录。
3. 机器可判断的格式、尺寸、大小、数量、时长和比例，报告 `已满足` / `不满足` / `无法读取`。
4. 核心玩法、图片是否误导、视频是否包含遮挡或配音等语义要求，报告 `需人工复核`；没有实际查看素材内容时不能说通过。
5. 读取最新 `review_rejected`。若审核原文涉及目标字段，单列“历史审核风险”，保留版本和原文；不要改写为官方规则。
6. 若字段或素材已经更换，只能说明“对象已变化”；确定性规则重新校验通过后才可说对应确定性检查已通过，语义问题仍是待复核。

推荐输出：

```text
当前字段
- 当前事实：...

官方规则
- [规则 ID] 要求摘要（文档名，章节，链接）

检查结果
- 已满足：...
- 不满足：...
- 需人工复核：...

历史审核风险
- 版本 + 审核原文；若没有则省略
```

## 提审前风险清单

用户明确要求提审后，在 `prepare-review-snapshot` 之前先按 skill analysis 读取当前资料、包体、版本、资质和历史审核；然后生成以下五组：

1. **确定性阻断项**：当前事实明确违反实时字段规格、动态必填、包体、资质或服务端约束。
2. **官方规则人工复核项**：官方规则明确存在，但 CLI 无法自动理解内容。
3. **历史审核风险**：最近的 `review_rejected` 原文，以及相关字段/包体是否变化。
4. **无法验证项**：没有当前素材内容、测试证据或接口能力，不能得出通过结论。
   - 注意：**视频转码/素材审核状态不属于「无法验证项」**。视频上传拿到 `videoId` 后即视为素材已提供，直接写字段；转码（只影响能否预览）和素材审核（提审后服务端异步判断）是后台流程，不是提审前风险清单要确认的内容，不要输出「素材审核状态未确认/无法验证」。仅当用户主动要求确认视频可播/素材库收录时，才用 materials 手册的 `get-video-detail` 查询。
5. **已通过项**：只列有当前、确定性证据的检查；不要把未检查事项列为通过。

每项至少包含：

```text
标题｜来源类型｜严重度｜检查状态｜证据｜官方章节（若有）｜下一步
```

严重度与处理：

| 状态 | 行为 |
| --- | --- |
| 当前确定性 blocker 或服务端 blocker | 停止，不进入正式提交 |
| 官方语义规则未复核 | 展示风险；不能自动宣称通过 |
| 历史问题对应对象未变化 | 高风险提示，要求用户先处理或明确说明已有何种证据 |
| 历史问题对应对象已变化但无验证证据 | 标记“已更换，仍待验证” |
| 指定测试明确失败 | 停止，并展示测试对象与结果 |
| 无接口或无证据 | 标记“无法验证”，不得默认为 0、无风险或已通过 |

生成本地风险清单不替代正式服务端流程。用户明确继续提审时，仍按相同 `release_schedule` 执行，并用本次 `precheck-app-review` 的结果复核：

`prepare-review-snapshot` → `precheck-app-review` → 单独最终确认 → `submit-app-review`

服务端返回的 blocker、warning、协议和 stale 始终优先；本地清单不能删减或覆盖服务端结果。

### 提审前主动提醒

在输出风险清单时，主动提醒用户：

> 请按当前游戏的发布目标和本次读取结果完善：简介、开发者的话、游戏截图、宣传图、实机视频，以及当前页面可见且适用的首页推荐相关素材或选项。游戏资料或版本审核通过不等于素材审核通过，也不等于已经具备首页推荐资格；缺失或不符合适用物料要求的项目，可能导致本次素材审核不通过并影响首页或编辑推荐展示。是否属于提审阻断项，以当前字段 `required`、服务端预检结果或适用官方物料要求为准。

这段提醒是检查清单，不是静态必填表。实机视频、1:1 宣传图、Windows 素材和首页编辑推荐栏目推荐图等项目，必须结合当前字段可见性、发布目标、官方章节和服务端返回判断。资料/版本审核、素材审核和首页推荐是不同判断；首页编辑推荐栏目推荐图缺失时，只能依据[游戏物料要求](taptap-suite/references/material-requirements.md)说明其专属栏目展示限制。访问路径和其他首页推荐结论必须以当前 `platform-status` 或其他直接状态证据为准。

## 视频交叉检查

官方事实：审核规范 2.6.10 写的是“实机录屏不得使用宣传视频替代实机录屏”。

- `trailer` 与 `gameplay_demo_video` 使用相同 `videoId`：可确定两个字段引用同一对象，应停止并要求使用不同素材。
- `videoId` 不同：只说明引用对象不同，不能证明视频内容不同或已经符合 2.6.10。
- 两份文档没有“高度雷同”的文字或相似度阈值。历史审核出现该表述时，只作为 `historical_review` 原文展示，并要求人工内容复核。

禁止输出：

```text
官方规范要求宣传片与实机录屏不得高度雷同。
```

允许输出：

```text
官方规则：审核规范 2.6.10 要求实机录屏不得使用宣传视频替代。
历史审核：版本 V-... 曾被反馈“宣传视频与实机视频内容高度雷同”。
当前验证：两个 videoId 不同，但 CLI 无法判断内容差异，需人工复核。
```

## 安装失败检查

两份指定文档只提供包名、Version Code、Version Name、更新日志和签名等安装包审核要求，没有具体手机型号的安装测试矩阵。

- 审核记录中的设备名称和安装失败是 `historical_review`。
- 当前 APK 是否更换来自 `current_fact`。
- 某设备安装是否成功只能来自 `test_evidence`。
- 没有测试证据时写“当前包体在该设备上的安装结果无法确认”，不能写“没有自动化测试，所以兼容性通过/失败”。

## 数据空值纪律

- 空数组、`null`、字段缺失和接口不可用不是数值 `0`。
- 没有趋势点不能推导 `flat` 或“变化 0”。
- 没有评价数据返回只能说“本次查询未返回评价数据”，不能扩大成平台绝对没有评价。
- 没有自动化测试接口只能说“当前 CLI 无法查询”，不能断言平台或游戏没有测试数据。
